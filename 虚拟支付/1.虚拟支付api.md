# 联调限制备忘

- 微信小程序虚拟支付沙箱使用 `env=1`
- `iOS` 不支持虚拟支付沙箱 `env=1`
- 因此 `iPhone + 0.01 + env=1` 不能作为沙箱验收路径
- 当前沙箱 `0.01` 验收请使用 `Android` 真机微信
- 若要验证 `iOS` 路径，需切正式环境 `env=0`，且准备 `>= 1元` 的虚拟支付商品
- 若开发者工具或自动化里再次看到 `requestVirtualPayment:fail automator capture only`，优先排查是否仍在使用抓参 mock、旧构建产物或旧 DevTools 会话
- 自动化脚本若通过 `微信开发者工具 cli auto` 拉起项目，结束后必须显式退出 automator 模式，再用普通 `open` 重新打开项目；否则后续手动点击支付也会被留在 `capture only` 态
- 若开发者工具运行的是 Windows 侧镜像项目，请同步核对镜像 `config.js` 与编译产物 `unpackage/dist/dev/mp-weixin/config.js` 的 `apiUrl`，避免误连到 `127.0.0.1:8088` 之类的旧本地调试地址

# 验收补充参数获取

适用场景：前端 UI 和后端接口需要额外保存这两个验收参数：

- `accepted runtime path`：本次支付到底跑在哪条真实运行路径上
- `payer / operator` 身份标签：谁是实际付款人，谁是实际操作人

## 1. accepted runtime path 如何获取

这个参数不是微信直接给你的单独字段，需要前端在拉起 `wx.requestVirtualPayment` 前，主动从小程序运行时拼出来。

### 前端可直接获取的字段

- `envVersion`：`wx.getAccountInfoSync().miniProgram.envVersion`
- `appId`：`wx.getAccountInfoSync().miniProgram.appId`
- `platform`：`wx.getSystemInfoSync().platform`
- `system`：`wx.getSystemInfoSync().system`
- `wechatVersion`：`wx.getSystemInfoSync().version`
- `sdkVersion`：`wx.getSystemInfoSync().SDKVersion`
- `scene`：`wx.getLaunchOptionsSync().scene`

说明：上面这组字段是当前项目真实已经采集并会被后端保留的字段范围。`brand`、`model` 虽然前端也能取到，但当前项目并没有随 `runtimeContext` 持久化。

### 推荐前端实现

```js
function getVirtualPaymentAcceptanceContext() {
  const accountInfo = typeof wx.getAccountInfoSync === 'function'
    ? (wx.getAccountInfoSync() || {})
    : {}
  const systemInfo = typeof wx.getSystemInfoSync === 'function'
    ? (wx.getSystemInfoSync() || {})
    : {}
  const launchOptions = typeof wx.getLaunchOptionsSync === 'function'
    ? (wx.getLaunchOptionsSync() || {})
    : {}

  return {
    envVersion: accountInfo.miniProgram?.envVersion || '',
    appId: accountInfo.miniProgram?.appId || '',
    platform: systemInfo.platform || '',
    system: systemInfo.system || '',
    wechatVersion: systemInfo.version || '',
    sdkVersion: systemInfo.SDKVersion || '',
    scene: launchOptions.scene ?? null
  }
}
```

这里建议直接把这组对象命名为 `runtimeContext`。`accepted runtime path` 是验收语义，不建议在当前项目里再额外包一层 `acceptedRuntimePath` 对象，否则容易和现有接口命名脱节。

### 推荐保存格式

不要只保存一句模糊文案，建议保存结构化 JSON，例如：

```json
{
  "envVersion": "trial",
  "appId": "wxbf57e6f2ba72b712",
  "platform": "android",
  "system": "Android 14",
  "wechatVersion": "8.0.48",
  "sdkVersion": "3.3.5",
  "scene": 1017
}
```

### 后端如何接收

前端在“创建虚拟支付订单”接口里，把它作为附加字段传给后端，例如：

```json
{
  "goodsId": 10001,
  "loginCode": "wx.login返回的code",
  "runtimeContext": {
    "envVersion": "trial",
    "appId": "wxbf57e6f2ba72b712",
    "platform": "android",
    "system": "Android 14",
    "wechatVersion": "8.0.48",
    "sdkVersion": "3.3.5",
    "scene": 1017
  }
}
```

后端建议原样落库到支付单扩展字段、调试表或支付审计日志里，不建议只打普通字符串日志。

## 2. payer 身份标签如何获取

`payer` 指的是“当前真正发起这笔虚拟支付的小程序登录用户”。

这个标签建议以后端为准，不要只信前端传参。

### 后端推荐取值来源

1. 从当前登录态 token 取商城 `user_id`
2. 由 `user_id` 查用户手机号 `mobile`
3. 由 `user_id + MP-WEIXIN` 查 `openid`
4. 如需联调标记，可再补一个 `isSandboxCandidate`

### 推荐保存格式

```json
{
  "userId": 10004,
  "mobile": "19900000000",
  "openidMasked": "oR1ZQ3***",
  "client": "MP-WEIXIN",
  "isSandboxCandidate": true
}
```

### 说明

- `payer` 可以自动获取
- 权威来源应是后端用户体系和 `user_oauth`
- `session_key` 只用于服务端签名，不建议放进 `payerContext` 或验收身份标签
- 前端最多只作为展示，不建议把 `payer` 身份完全交给前端决定

## 3. operator 身份标签如何获取

`operator` 指的是“谁在操作这次测试”。

这个字段通常不是微信支付接口天然返回的，也不是 `wx.requestVirtualPayment` 的参数。它是否能自动拿到，取决于你的测试方式。

### 情况 A：用户自己在手机里直接支付

如果没有 DevTools 操作员、没有体验版上传人、没有额外代测人员，则可以直接认定：

```json
{
  "role": "self",
  "sameAsPayer": true
}
```

### 情况 B：有人代为操作 DevTools / 上传体验版 / 生成二维码

这类 `operator` 微信不会自动暴露给小程序前端，建议走“人工录入 + 后端保存”。

推荐在你的测试 UI 或后台表单里增加字段：

- `operatorName`
- `operatorSource`
- `sameAsPayer`
- `remark`

推荐保存格式：

```json
{
  "operatorName": "张三",
  "operatorSource": "devtools-preview",
  "sameAsPayer": false,
  "remark": "体验版上传人/二维码生成者"
}
```

### 结论

- `operator` 不能指望从 `wx.requestVirtualPayment` 自动拿到
- 若业务一定要留痕，最稳妥方式是前端 UI 或后台管理页手工选择/录入，再和支付单一起保存

## 4. 推荐前后端最终入参结构

如果你现在要写一个简单前端 UI 和后台接口，建议一次性把这三个对象一起传：

```json
{
  "goodsId": 10001,
  "loginCode": "wx.login返回的code",
  "runtimeContext": {
    "envVersion": "trial",
    "appId": "wxbf57e6f2ba72b712",
    "platform": "android",
    "system": "Android 14",
    "wechatVersion": "8.0.48",
    "sdkVersion": "3.3.5",
    "scene": 1017
  },
  "operatorContext": {
    "operatorName": "张三",
    "operatorSource": "devtools-preview",
    "sameAsPayer": false,
    "remark": "本次测试由PC端操作员辅助发起"
  }
}
```

其中：

- `runtimeContext`：前端自动采集
- `payerContext`：后端根据当前登录用户自动补齐
- `operatorContext`：前端 UI 手工录入或后台手工选择

如果后续你确实还想额外保留 `brand`、`model`，可以另加字段，但不要冒充“当前项目默认已采集并落库”。

## 5. 当前项目建议口径

当前项目虚拟支付沙箱验收口径仍然是：

- `Android` 真机微信
- `env=1`
- `0.01` 商品

因此 `accepted runtime path` 至少要能证明：

- `platform` 是安卓真机路径，而不是单纯 `devtools`
- `envVersion` 是 `develop` 或 `trial`
- 当前支付参数里的 `env` 是 `1` 还是 `0`
- 微信版本、SDK 版本、场景值有实际记录

否则后续看到 `status=6`、`access denied`、`automator capture only` 之类问题时，很难区分到底是配置错、身份错，还是运行路径错。

## 6. 当前项目可复用签名逻辑

当前项目已经有一套可直接复用的虚拟支付签名实现，不建议在新项目里重新手写一遍。默认做法应该是“迁移现有实现或做薄封装”，而不是重新发明签名规则。

### 6.1 小程序支付参数签名

代码位置：`/opt/yoshop/yoshop2.0/app/api/service/cashier/Payment.php`

当前项目在生成虚拟支付参数时，会统一组装：

- `signData`
- `paySig`
- `signature`
- `mode`

关键口径：

```text
paySig = hash_hmac('sha256', 'requestVirtualPayment&' + signData, appKey)
signature = hash_hmac('sha256', signData, session_key)
```

其中：

- `appKey` 按 `env` 选择沙箱或现网配置
- `session_key` 优先使用本次 `wx.login` + `loginCode` 刷新的新值，失败后才回退到当前登录用户的小程序旧登录态
- 当前实现还会把 `runtimeContext` 作为 `client_runtime` 写入支付追踪日志，方便后续验收和排障

### 6.2 session_key 来源

代码位置：

- `Payment.php` 中的 `resolveWechatSessionKey()` / `getWechatSessionKey()`
- `/opt/yoshop/yoshop2.0/app/common/model/UserOauth.php`

当前实现并不是简单地“只读旧登录态”。真实逻辑是：

1. 优先使用这次下单请求里随 `wx.login` 一起带来的 `loginCode`
2. 服务端用 `loginCode` 向微信换取新的 `session_key`
3. 如果刷新失败，再回退到 token / `user_oauth` 里的旧登录态

这样做是为了尽量降低虚拟支付 `signature` 因旧登录态过期而失败的概率。

这也是为什么 `payer` 身份标签建议以后端为准。

### 6.3 服务端调用微信 xpay 接口签名

代码位置：`/opt/yoshop/yoshop2.0/app/common/library/wechat/VirtualPayment.php`

当前封装已经覆盖：

- `/xpay/query_order`
- `/xpay/refund_order`
- `/xpay/notify_provide_goods`

关键口径要分两类：

```text
pay_sig = hash_hmac('sha256', uri + '&' + body, appKey)
```

其中：

- `/xpay/query_order`
- `/xpay/refund_order`

会走 `signedPost()`，因此会附带 `pay_sig`。

但要特别注意：

- `/xpay/notify_provide_goods`

在当前项目实现里不带 `pay_sig`，只带 `access_token`。

这部分签名和前端 `wx.requestVirtualPayment` 的 `paySig` 不是一回事，文档和代码里都要明确区分，避免混用。

### 6.4 新项目复用建议

如果要在新的独立虚拟支付小程序里复用当前能力，建议按这个优先级处理：

1. 直接复用当前签名公式和参数结构
2. 如项目目录结构不同，只做最小封装迁移
3. 仅在微信官方规则发生变化时，才重新调整签名实现

当前仓库内的实现，与现有项目文档和微信官方虚拟支付文档口径一致，可视为当前默认有效版本。
