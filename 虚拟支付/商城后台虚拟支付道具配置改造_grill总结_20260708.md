# 商城后台虚拟支付道具配置改造 - Grill 总结

日期：2026-07-08
状态：已完成 grill / 已完成一次子代理 review / 尚未开始实施代码

## 1. 目标

打破微信虚拟支付道具参数与小程序代码的硬编码绑定，将道具配置能力迁移到商城后台可视化界面。

改造完成后：
- 新增、编辑虚拟支付商品时，无需修改代码
- 无需重新发布小程序版本
- 在商城后台即可完成价格驱动的道具参数生成与校验

## 2. 方案选择

已确认采用 **方案 B**：
- **不新增独立道具中心**
- **只在现有商品新增/编辑页增强虚拟支付配置能力**

选择原因：
- 改动最小
- 最大程度复用现有商品、后台、支付链路
- 符合奥卡姆剃刀

## 3. 核心原则

### 3.1 唯一价格源
- 只认商品单规格售价 `goods_price`
- 不新增单独的“虚拟支付价格”字段

### 3.2 后端是规则 owner
- 前端只负责联动展示、预校验、交互优化
- 真正的规则校验与收口，必须在后端保存链路完成

### 3.3 `vp_product_name` 是镜像字段
- 主要服务后台可视化、运营识别、回显和校验
- 不进入支付核心逻辑
- 支付核心继续依赖：
  - `vp_enabled`
  - `vp_product_id`
  - `vp_price_snapshot`

### 3.4 最小改造边界
- 不建独立道具中心
- 不批量修复历史数据
- 不对支付主协议做大改
- 不把订单商品快照重构纳入本次范围

## 4. 已确认业务规则

### 4.1 自动生成规则

#### 价格 >= 1 元
- 必须是整数
- `productId = vip + 整数价格`
- `productName = productId`
- 例如：
  - `158 -> vip158`
  - `88 -> vip88`

#### 价格 < 1 元
- 先换算成分
- 左侧补零到至少三位
- `productId = vip + 三位数字`
- `productName = productId`
- 例如：
  - `0.01 -> vip001`
  - `0.11 -> vip011`

### 4.2 保存规则
开启虚拟支付时，必须同时满足：
- 商品必须是单规格
- 商品必须是服务商品
- 商品价格必须大于 0
- `< 1 元` 按三位分规则
- `>= 1 元` 必须为整数
- `vp_product_id` 必须与规则匹配
- `vp_product_name` 必须与规则匹配
- `vp_price_snapshot` 必须等于价格换算出的分值

任何一项不满足：
- **直接禁止保存**

### 4.3 表单交互规则
- 保留手动修改入口
- 但最终保存值仍必须符合规则
- 不新增 `auto/manual` 模式字段
- 通过“当前值是否等于规则推导值”判断当前是否处于自动态

### 4.4 价格快照规则
- `vp_price_snapshot` 改为 **只读展示**
- 不允许手输
- 由系统根据 `goods_price` 自动计算

### 4.5 历史数据策略
- 不做批量修库
- 老数据可查看
- 一旦编辑并保存，就必须符合新规则
- `9.9` 这类 `>= 1 元但非整数` 的值，以后不允许继续保存

## 5. 需要新增/保留的数据字段

### 5.1 已有字段
- `vp_enabled`
- `vp_product_id`
- `vp_price_snapshot`

### 5.2 本次新增字段
- `vp_product_name`

### 5.3 明确不新增的字段
- 不新增独立道具表
- 不新增 `vp_config_mode` / `auto_manual_mode` 一类字段
- 不新增独立“虚拟支付价格”字段

## 6. 建议实施顺序（供 Trellis 接手）

### Step 1：数据库最小变更
目标：只补最小必要字段

- 为商品表新增 `vp_product_name`

说明：
- 这是满足“名称回显、手动入口、校验闭环”的最小必要字段
- 不新增额外模式字段

### Step 2：先改后端规则收口
重点文件：
- `yoshop2.0/app/store/model/Goods.php`

要求：
1. 接收并处理 `vp_product_name`
2. 封装统一规则推导逻辑：
   - 输入：`goods_price`
   - 输出：
     - `vp_product_id`
     - `vp_product_name`
     - `vp_price_snapshot`
3. 保存时执行完整校验：
   - 单规格
   - 服务商品
   - 价格 > 0
   - `< 1 元` 三位分规则
   - `>= 1 元` 必须整数

   - `vp_product_id`

关键原则：
- **后端必须把 `goods_price` 当唯一真相源**
- 不要只信前端提交值
- 更稳的做法是：后端自行推导规则值，再校验或覆盖提交值

## 7. 已知边界与风险（需明确给业务/运营）

### 7.1 商城后台生成成功，不等于微信侧道具已存在
例如：
- 商城里商品价格填 `158`
- 系统自动生成 `vip158`
- 但如果微信虚拟支付后台没有已创建/已发布 `vip158`
- 支付依然会失败

结论：
- 本次改造解决的是“后台配置不再改代码、不再发版”
- **不解决微信侧道具是否已创建/已发布这个外部事实**

建议把这条写进交付说明或后台提示文案。

### 7.2 历史数据会在“保存时收口”
- 旧的 `9.9` 虚拟支付商品，在未编辑前可能继续按旧配置工作
- 一旦进入编辑并保存，即使只是改别的字段，也可能因为新规则被拦截

这不是 bug，是预期行为。

### 7.3 未支付旧订单可能受当前商品配置影响
当前支付链路对未支付订单存在按当前商品配置回补的逻辑。

这意味着：
- 订单先创建
- 后续商品又改了虚拟支付配置或价格
- 旧未支付订单在支付时，可能受当前商品配置影响

结论：
- 这是当前系统既有边界
- 本次不扩范围重构订单侧快照
- Trellis 实施时只需明确为已知边界

## 8. 验收标准

1. 开启虚拟支付后，后台可自动生成：
   - `vp_product_id`
   - `vp_product_name`
   - `vp_price_snapshot`

2. 商品价格变化时，后台联动更新上述字段

3. `>= 1 元` 非整数价不能保存
   - 例如：`9.9` 必须报错

4. `< 1 元` 时能正确生成三位规则
   - `0.01 -> vip001`
   - `0.11 -> vip011`

5. 手动修改入口存在，但保存时仍必须符合规则

6. 关闭虚拟支付时，相关字段自动清空

7. 编辑旧数据时，如果不符合新规则，保存会被拦截

8. 支付链路无需改协议，现有 `Payment.php` 仍能消费新配置

## 9. 子代理 Review 结论摘录

子代理 review 的核心结论：

- 但必须坚持：

  - **`goods_price` 是唯一价格源**
  - **`vp_product_name` 只是镜像字段，不是支付核心字段**
- 如果主要依赖前端联动而不在后端收口，不建议实施
