# 腾讯云生产重建与可持续部署

## Goal

将 `/opt/yoshop` 当前可运行的新版本安全迁移到腾讯云 `124.222.144.181`，以 `https://wx.gxwqb.cn` 为正式业务入口，并建立可重复、可回滚、不会覆盖生产数据的一键发布体系；同时清理本地仓库与服务器历史垃圾，保留完整开发能力、有效 Git 历史、备案静态页、Docker/containerd、证书、Komari 和腾讯云代理。

## Background

- 本地 WSL 通过 Cloudflare Tunnel 域名 A `https://wx.oiob.cn` 支持开发版/体验版联调；腾讯云正式域名 B 为 `https://wx.gxwqb.cn`。
- 腾讯云旧商城代码、数据库、订单和备份均可清除；首次新生产仅迁移本地商品、商城配置、页面装修及被引用图片，不迁移测试用户、订单、退款、支付和余额流水。
- 腾讯云 Ubuntu 22.04 系统盘约 69 GiB，旧 Timer 因 PHP 8.3/Workerman 异常重启循环产生约 19 GiB Workerman 日志、32 GiB syslog 和 3.9 GiB journal，磁盘曾达到 94%。
- Git 当前约 34 个有效提交、65 个未提交变更；历史错误追踪过 `unpackage`、前端编译产物和 uploads。有效历史必须保留，原 GitHub 地址 `git@github.com:unixcs/uni-app.git` 继续使用。
- 用户已确认历史成功 SSH 登录 IP 均可视为本人使用网络；未发现成功入侵的明确证据。现有 SSH 密钥本轮继续使用，任务结束只交付手动轮换指南，不自动换钥。

## Requirements

### R1 — 安全与恢复优先

1. 任何 Git 历史重写、本地删除或服务器清理前，必须先建立可验证恢复点。
2. 服务器进入破坏性阶段时，先导出审计/配置资料，再停止失控 Timer；规划阶段不得提前修改服务器。
3. 优先创建腾讯云系统盘快照；无法创建时，至少把关键配置、证书元数据、数据库结构、审计摘要和运维资料复制到服务器之外。
4. 每个破坏性阶段都必须有回滚点和验证门。

### R2 — 本地仓库与开发能力

1. 精准忽略依赖、日志、缓存、本地环境、uploads、支付证书、runtime 和生成产物。
2. 保留 `node_modules`、PHP `vendor` 和本地私有配置，确保 PHP/Nginx、本地测试、三个前端构建及 WSL→Windows 小程序编译链路可继续使用。
3. 保留全部有效业务修改和 34 个有效历史提交；按逻辑提交当前改动，过滤历史垃圾后使用 `--force-with-lease` 更新原 GitHub `main`。
4. Windows 小程序目录只作为 WSL 单向覆盖的构建镜像。

### R3 — 确定性发布工具与 Skill

1. 提供单一人工入口 `./deploy.sh production`，底层由无第三方依赖的 Python 控制器和服务器 Bash 发布脚本执行。
2. 创建项目级 `$yoshop-deploy` Skill，负责检查、解释、两次授权和调用确定性程序；Skill 不临时拼接生产步骤。
3. 每次生产发布从已提交且已推送的 `main` 提交创建干净完整运行包；本地完成依赖准备、H5/admin/store 构建和测试，服务器不依赖 GitHub/npm/Composer 网络。
4. 生产发布默认完整构建；微信小程序测试/生产构建与服务器发布分离。
5. 发布包必须有清单、提交号、校验值和敏感文件扫描结果。

### R4 — 双环境与客户端兼容

1. 域名 A 永远只用于 WSL 开发/体验测试；域名 B 永远只用于腾讯云生产。
2. 提供固定测试/生产小程序构建命令并验证最终产物域名；禁止手工改 URL 作为发布步骤。
3. 修复当前异步临时覆盖 `config.js` 的时序风险和 Windows 镜像 `rsync --delete` 目标保护。
4. 发布顺序为 A 本地测试 → B 兼容后端 → 体验版连接 B 验证 → 正式小程序发布；后端必须兼容当前线上旧客户端。

### R5 — 腾讯云基础设施重建

1. 保留 Ubuntu 22.04、Nginx、PHP 8.3、MySQL 8、Redis、Docker/containerd、Certbot、Komari、腾讯云代理、SSH 和系统必要服务。
2. 清除旧商城源码、前端依赖、旧数据库/备份、开发工具、无用预装组件和异常日志；Docker 软件保留，备案静态页由宿主机 Nginx 直接提供。
3. 首次重建期间 B 返回 503 维护页；`www.gxwqb.cn`/`gxwqb.cn` 备案页和 ACME 路径保持可用。
4. 创建受限 `deployer` 用户；本轮临时复用现有公钥，禁止赋予无限制 sudo。
5. 配置 UFW/安全边界、Fail2ban、2 GiB swap、日志轮转/上限和磁盘发布门槛。

### R6 — 代码与数据分离

1. 采用 `/opt/yoshop/releases/<release>` + `/opt/yoshop/current` 原子切换结构。
2. 永久共享数据仅包括生产 env、uploads、支付证书/私钥、部署状态和数据库；普通 runtime 按版本隔离。
3. 生产缓存与会话迁移到 Redis并分前缀/DB；应用日志统一到 `/var/log/yoshop`。
4. 支付私钥不进入 Git/发布包，使用最小文件权限。

### R7 — 数据初始化、迁移与备份

1. 首次初始化使用白名单基线：保留商品、SKU、分类、页面、必要配置和被引用图片；清除用户、OAuth、订单、退款、支付、余额、反馈、队列和日志。
2. 首次初始化脚本不得被日常发布调用。
3. 后续数据库变更使用有校验值和执行记录的增量迁移；自动发布禁止破坏性 SQL。
4. 迁移前自动备份；MySQL binlog 保留 7 天，本地完整备份保留 7 天，恢复流程必须验证。
5. COS/CAM 异地备份本轮暂缓，发布报告必须明确灾难恢复目标尚未完全达成。

### R8 — 发布、回滚与可观测性

1. 新版本上传到独立目录，检查通过后原子切换；失败自动切回上一兼容版本。
2. 保留最近 5 个版本和当前稳定版本。
3. 提供公开最小 `/healthz` 与 SSH 内部深度检查；验证 H5、API、admin、store、uploads、备案页和证书。
4. Timer 连续异常或日志异常增长时自动熔断；部署在磁盘、备份、迁移、Nginx或健康检查异常时拒绝执行。
5. 日志保留 14 天，journal 上限约 1 GiB；禁止 Workerman 向 `vendor` 写日志。

### R9 — 人工授权与运维知识

1. Git 提交与生产发布是两次独立授权；脚本不自动提交，也不在未授权时修改服务器。
2. 重构 `/mnt/vps/tencent` 为私有运维知识库；移除明文密码和过期重复内容，以 `/mnt/vps/tencent/static-site/index.html` 为备案页唯一事实源。
3. 交付手动 SSH 密钥轮换指南，但本轮不自动更换现有密钥。
4. 每次发布输出可审计报告；不得直接在腾讯云修改业务代码。

## Constraints

- 不依赖腾讯云稳定访问 GitHub。
- 不删除本地开发依赖；本地目录仍可约 1.3 GiB。
- 不重装操作系统，不升级 Ubuntu 24.04。
- 不删除 Docker/containerd。
- COS 外部备份与外部通知渠道暂不阻塞首次上线。
- 任何秘密不得写入 Git、Trellis、Skill、Markdown、命令输出或发布日志。
