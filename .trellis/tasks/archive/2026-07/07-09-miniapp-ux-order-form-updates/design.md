# 设计说明：Miniapp UX and order form updates（父任务）

## 1. 父任务定位

该任务现在的设计目标不是继续承载所有代码级实现细节，而是作为：
- 总需求真相源
- 子任务映射中心
- 跨子任务依赖说明
- 最终集成验收与发布顺序说明

因此父任务 design 只保留 **边界设计** 与 **协同设计**；具体模块设计下沉到各自子任务。

## 2. 子任务边界

### Child A：首页弹窗 + 隐私协议单例内容
拥有：
- `wxapp_setting.basic` 单例配置扩展
- 首页首登弹窗显示链路
- `user.first_login_popup_seen_time` 账号级单次触达状态
- 隐私协议专页与“我的”页隐私入口

不拥有：
- 反馈提交/记录/后台处理
- 服务订单契约与后台搜索改造

### Child B：反馈 / 投诉 MVP
拥有：
- 反馈数据表与状态流转
- 小程序反馈提交、记录列表、详情页
- 商家后台反馈处理页
- “我的”页反馈入口

不拥有：
- 首页业务弹窗
- 隐私协议单例内容
- 服务订单契约与历史清理

### Child C：服务订单契约升级 + 搜索 + soft delete hide
拥有：
- `service_contact` 新字段契约
- checkout / order detail / store list/detail/export/search 同步改造
- 历史服务订单 soft delete hide 命令与上线顺序

不拥有：
- 反馈工单流程
- 首页弹窗与隐私协议内容

## 3. 跨子任务依赖设计

### 3.1 Child A ↔ Child B 共享文件协调
共享文件：
- `yoshop2.0-uniapp/pages/user/index.vue`
- `yoshop2.0-uniapp/pages.json`

协调策略：
- 推荐先启动 Child A，由 A 完成“我的”页服务入口结构的第一轮稳定改动；
- Child B 在 A 落地后的文件结构上继续增加反馈入口与反馈页面注册；
- 若 B 先启动，也必须吸收 A 的结构性改动，不能覆盖回旧布局。

这属于**文件级依赖**，不是运行时依赖；必须写入子任务 artifact，避免树结构误导。

### 3.2 Child C 的独立性与内部顺序
Child C 与 A/B 没有功能依赖，但它内部有严格顺序：
1. 先完成提交契约、展示契约、搜索契约统一；
2. 做新订单 smoke test；
3. 再在维护窗口执行历史服务订单 soft delete hide。

因此 C 不能把“代码改造”和“历史清理执行”视为同一个原子步骤。

## 4. 集成验收设计

父任务持有跨子任务验收，而不是把最终验收拆碎后丢失：
- 首页：微信隐私弹窗与业务弹窗不会冲突；
- 我的：隐私协议与反馈入口共存且可访问；
- 反馈：用户看到的 issue type / 状态 / 官方回复与后台处理一致；
- 服务订单：新字段文案、导出字段、搜索字段与平台筛选保持同一语义；
- 历史清理：只隐藏服务订单，可人工恢复，不影响非服务订单。

## 5. 发布与回滚边界设计

### 5.1 Child A 回滚边界
- 页面与接口问题时，可先通过设置关闭业务弹窗；
- `first_login_popup_seen_time` 为增量字段，可在停用功能时保留不回收；
- 隐私协议入口与专页问题可独立回退，不影响订单主链路。

### 5.2 Child B 回滚边界
- 反馈模块是新增能力，可通过隐藏入口、菜单、路由实现“功能关闭”；
- 反馈表保留即可，不影响订单/支付主链路；
- 后台回复与状态流转失败不会破坏现有下单流程。

### 5.3 Child C 回滚边界
- 代码回滚与历史数据回滚必须分开定义；
- soft delete hide 只写 `is_delete=1`，必要时可人工恢复；
- 由于涉及订单视图与搜索回归，必须把 C 放在最后集中验证。

## 6. 结论

父任务现在的正确形态是：
- **保留**：完整需求、决策、子任务映射、集成验收、推荐顺序；
- **下沉**：具体设计细节、实施清单、回滚点到各子任务。

因此，父任务不应再作为直接实现目标启动；真正进入 Phase 2 时，应从推荐的子任务开始逐个启动。
