# 商城后台虚拟支付道具配置改造

## Goal

按方案 B 在现有商品新增/编辑页完成最小改造，把微信虚拟支付道具配置从小程序代码硬编码迁移到商城后台可视化配置；在不扩支付核心逻辑范围的前提下，实现基于 `goods_price` 的自动推导、回显与后端保存收口。

## Requirements

### 业务目标
- 运营在商城后台新增或编辑虚拟支付商品时，无需改代码、无需重新发布小程序。
- 虚拟支付商品的道具配置由商品单规格售价驱动生成。
- 后台页面需要支持展示、联动更新、错误提示与编辑旧数据。

### 核心原则
- `goods_price` 是唯一价格源；不新增独立“虚拟支付价格”字段。
- 后端是规则 owner；前端只能做联动展示、预校验和交互优化。
- `vp_product_name` 仅用于后台可视化、运营识别、回显和校验，不进入支付核心逻辑。
- 支付核心继续依赖 `vp_enabled`、`vp_product_id`、`vp_price_snapshot`。
- 仅做最小改造：不建独立道具中心、不批量修历史数据、不重构订单快照、不改支付主协议。

### 自动生成规则
- 当价格 `>= 1` 元时：
  - 必须是整数。
  - `productId = vip + 整数价格`。
  - `productName = productId`。
- 当价格 `< 1` 元时：
  - 按分换算。
  - 左补零到至少 3 位。
  - `productId = vip + 三位数字`。
  - `productName = productId`。

### 保存规则
- 开启虚拟支付时，商品必须同时满足：
  - 单规格。
  - 服务商品。
  - 商品价格大于 0。
  - `< 1` 元按三位分规则生成。
  - `>= 1` 元必须是整数。
  - 保存结果中的 `vp_product_id`、`vp_product_name`、`vp_price_snapshot` 与规则一致。
- 关闭虚拟支付时，需要清空 `vp_product_id`、`vp_product_name`、`vp_price_snapshot`。

### 数据范围
- 商品表新增 `vp_product_name` 字段。
- 不新增独立道具表。
- 不新增模式字段，例如 `vp_config_mode` / `auto_manual_mode`。

### 已知边界
- 后台成功生成配置，不等于微信虚拟支付后台已经存在并发布对应道具。
- 旧商品一旦重新保存，将按新规则收口，不符合规则的数据会被拦截。
- 未支付旧订单仍受现有订单/商品回补边界影响，本次不重构订单侧快照。

## Acceptance Criteria

- [ ] 商品表新增 `vp_product_name`，新增/编辑商品时可读写并正确回显。
- [ ] 开启虚拟支付后，后台可自动生成 `vp_product_id`、`vp_product_name`、`vp_price_snapshot`。
- [ ] 商品价格变化时，后台联动更新上述三个字段。
- [ ] `>= 1` 元的非整数价格不能保存，例如 `9.9` 必须报错。
- [ ] `< 1` 元时可正确生成三位规则，例如 `0.01 -> vip001`、`0.11 -> vip011`。
- [ ] 前端存在手动修改入口，但保存时仍只能落库符合规则的值。
- [ ] 关闭虚拟支付时，相关字段会被自动清空。
- [ ] 编辑旧数据时，如不符合新规则，保存会被后端拦截。
- [ ] 支付链路不改协议，现有 `Payment.php` 继续只消费 `vp_product_id` 与 `vp_price_snapshot`。
