# 修复小程序支付成功后重复拉起收银台

## Goal

从支付链路的基本不变量出发，修复微信小程序体验版中“用户已经完成支付，但页面未收口到已支付状态，随后又进入第二次支付并出现相同金额风险提示”的问题，保证一次明确的用户支付意图最多产生一次有效收款尝试，支付结果不确定时优先查单而不是再次扣款。

## Background / Confirmed Facts

- 故障发生在微信小程序体验版的服务订单收银台，使用 `wx.requestVirtualPayment` 虚拟支付链路。
- 前端入口位于 `yoshop2.0-uniapp/pages/checkout/cashier/index.vue`；微信支付封装位于 `yoshop2.0-uniapp/core/payment/wechat.js`。
- `wx.requestVirtualPayment` 成功只代表客户端支付 API 返回成功；订单最终状态必须以后端异步通知或主动查单为准。
- 发起虚拟支付前，前端会把 `outTradeNo` 写入 `tempUnifyData_<orderId>`，用于页面重新显示后的恢复查单。
- 小程序从微信支付层返回时会触发收银台页面 `onShow()`；当前 `onShow()` 会立即调用 `getCashierInfo()`，随后 `performance()` 可能立刻消费临时交易号并发起查单。
- 原生支付 `success` 回调也会调用 `onTradeQuery()`。如果 `onShow()` 恢复查单先占用了 `isTradeQuerying`，支付成功回调中的查单会直接返回，而不会加入已有查单或安排后续重试。
- 当前 `onTradeQuery()` 对后端 `isPending=true` 没有等待收口分支，而是进入失败提示；这会让“微信已支付、后端仍处于 CREATED/PAYING 或通知尚未落库”的短暂窗口停留在收银台。
- `handleSubmit()` 的外层 Promise 没有等待 `Wechat.payment()` 和后续查单完成；支付拉起后约 10ms 即重新解除 `disabled`，无法覆盖整个支付/确认周期。
- 后端每次 `orderPay` 都会生成新的虚拟支付 `outTradeNo`，并按设计保留同一订单的多次支付尝试。因此一旦前端在首笔支付尚未收口时再次提交，会真实创建第二笔同金额支付尝试，并触发微信的重复金额风险提示。
- 现有后端主动查单可在微信状态为 paid / paid-pending-delivery 时调用订单支付成功服务完成本地收口；缺口主要在前端竞态、等待策略和二次支付防线。

### Production Forensics (2026-07-14)

- 真实体验版日志证明，同一主订单在首笔支付完成前已经调用了两次 `cashier/orderPay`：
  - 订单 `10521`：第一次 `19:07:09` 创建交易 `335497465526651242`；第二次 `19:07:14` 创建交易 `335497488020711156`；第一笔实际付款时间为 `19:07:19`，本地在 `19:07:21` 收口。
  - 订单 `10522`：第一次 `19:07:35/36` 创建交易 `335497578612800554`；第二次 `19:07:40` 创建交易 `335497596675959427`；第一笔实际付款时间为 `19:07:48`，本地在 `19:07:49` 收口。
- 两个样本均是“第二笔交易先被创建，第一笔随后才支付成功”；因此用户看到的“支付成功后又弹一次收银台”不是支付成功后系统才新建交易，而是支付前已经发起的第二个 `wx.requestVirtualPayment` 在第一层收银台关闭后继续显示。
- 当前仓库只有收银台按钮 `handleSubmit()` 会调用 `CashierApi.orderPay()`；每个样本相隔 4–5 秒的两次服务端入口证明客户端提交防重锁已提前释放。
- `handleSubmit()` 外层 Promise 只等待 `orderPay` 返回；`onSubmitCallback()` 没有 return `Wechat.payment()`，所以 `.finally()` 在原生支付仍进行时就执行并于 10ms 后将 `disabled=false`。
- 当前未提交的 iOS 退款改动没有修改收银台页面、微信支付封装或 cashier 服务入口。相关改动触及共享 `payment_trade` 快照/行锁和通知处理，可能改变少量处理时序，但没有证据表明它们生成了第二次 `orderPay`，因此不是重复拉起的直接根因。
- 真正相关的支付恢复逻辑来自提交 `89faf7c`（2026-07-07 23:54:01，`feat: sync virtual payment updates`）：该提交把原本 H5-only 的 `performance()` 恢复逻辑扩展到小程序，并加入非 H5 自动查单；它还保留了支付 Promise 未返回、按钮提前解锁的问题。
- 本地支付源文件最后修改于 2026-07-07，但当前体验版编译产物生成于 2026-07-14 08:36。最合理的发布解释是：最近为 iOS 退款重新编译/上传体验版时，同时把 7 月 7 日已经存在但此前未进入该体验包或未被触发的支付缺陷一起带了进去。

## First-Principles Invariants

1. **支付只能由明确用户意图触发**：页面 `onShow`、状态刷新、查单重试都不得调用 `orderPay` 或再次拉起微信收银台。
2. **一次用户意图对应一个活动交易号**：首笔交易结果未确认前，不创建第二个 `outTradeNo`。
3. **未知不等于失败**：微信状态仍在处理或本地通知尚未落库时，应保持“确认中”并继续有限查单，不能恢复可支付状态。
4. **服务端状态是最终事实源**：客户端 success 只启动收口流程；跳转必须以主动查单、异步通知后的订单已支付状态为准。
5. **成功收口幂等**：并发的 `onShow`、原生 success、异步通知和定时查询只能触发一次成功提示和一次页面跳转。
6. **取消与不确定分离**：用户明确取消可以解除支付锁；网络错误、查询处理中或回调竞态不能当作取消。
7. **后端提供最后一道防线**：已有未终态虚拟交易时，新建支付尝试前必须先确认旧交易没有成功证据；无法确认时宁可暂缓二次支付，也不能冒重复扣款风险。

## Requirements

### R1. 前端支付状态机

- 收银台必须区分 `idle / creating / cashier_open / confirming / success / cancelled / failed` 等等价状态，而不是仅依赖一个会过早释放的 `disabled` 布尔值。
- 从提交下单开始，到明确成功、明确取消或明确失败之前，“确认支付”不得再次触发 `orderPay`。
- `onSubmitCallback()` 必须把微信支付 Promise 和后续收口 Promise 返回给调用链，不能在原生收银台刚拉起时就释放按钮锁。

### R2. 合并支付返回与页面恢复查单

- `onShow()` 和 `wx.requestVirtualPayment.success` 必须进入同一条查单收口流程。
- 同一交易号同时请求查单时，后发调用应复用/等待当前查单，不得静默丢失。
- 支付收银台仍处于活动阶段时，`onShow()` 不得把临时交易号误当作“遗留支付”并抢先执行一次不可恢复的查单。

### R3. 有界轮询与最终状态

- 后端返回 `isPay=true` 时立即执行一次幂等成功收口。
- 后端返回 `isPending=true` 时进入短时有界轮询；轮询期间保持支付锁和“支付结果确认中”语义，不允许再次付款。
- 轮询期间也应刷新本地订单状态，以兼容异步通知先落库、主动查单稍后返回的情况。
- 轮询耗尽但仍不确定时，明确提示用户结果仍在确认，并保留旧交易号供后续恢复查单；不得自动再次拉起支付。
- 明确取消时清理本次恢复数据并恢复可支付状态。

### R4. 成功导航幂等

- 并发成功信号只能显示一次成功提示、触发一次 `syncRefresh`、执行一次导航。
- 成功后清理当前订单的临时交易号和虚拟支付失败缓存。

### R5. 后端二次支付防线

- 对同一订单已有最新虚拟支付尝试且本地订单仍待支付的情况，新建交易号前先检查旧交易的权威状态。
- 旧交易已支付或有明确已支付证据时，完成本地订单收口并向前端返回“已支付”，不得生成新交易号。
- 旧交易结果无法确认时，不生成新交易号，返回可识别的“支付结果确认中”。
- 只有旧交易明确未支付、已关闭或用户明确取消后，才允许创建新的支付尝试。
- 保持现有异步通知、主动查单、重复通知及多交易历史记录的幂等能力。

### R6. 兼容性

- 普通微信支付、支付宝、余额支付和 H5 恢复确认流程不得被破坏。
- 修复优先限定在微信小程序虚拟支付分支；共享函数的变更必须覆盖现有客户端分支。
- 不覆盖或回退工作区内与退款、商家后台等其他任务相关的未提交修改。

## Acceptance Criteria

- [ ] AC1：Android 微信小程序体验版完成一次虚拟支付后，页面进入“订单已支付”收口并正常跳转，不会再次调用 `wx.requestVirtualPayment`。
- [ ] AC2：支付成功后，即使首次主动查单返回 `isPending=true`，前端也会继续有界查单且按钮保持锁定；最终查到成功后只提示和跳转一次。
- [ ] AC3：`onShow()` 恢复查单与原生 success 回调同时发生时，不会丢失成功收口，也不会并发创建第二个 `outTradeNo`。
- [ ] AC4：支付结果确认期间连续点击“确认支付”，后端 `cashier/orderPay` 与 `wx.requestVirtualPayment` 均只调用一次。
- [ ] AC5：用户明确取消支付后，不自动查单，不显示“支付确认中”，并可由用户再次明确发起新支付。
- [ ] AC6：结果未知或网络异常时，不自动再次拉起收银台；页面提示结果确认中并保留原交易号供恢复。
- [ ] AC7：后端发现旧虚拟交易已支付时完成订单收口且不生成新交易号；旧交易状态无法确认时也不生成新交易号。
- [ ] AC8：支付成功导航具备幂等保护，重复 success / onShow / 查单响应不会造成重复 toast、重复事件或重复导航。
- [ ] AC9：增加可自动执行的前端竞态回归测试，至少覆盖 pending→paid、onShow 与 success 并发、连续点击、取消支付和成功幂等。
- [ ] AC10：相关 PHP 文件通过 `php -l`，小程序相关测试和 `build:mp-weixin` 通过，编译产物包含本次防重复收口逻辑。

## Out of Scope

- 调整微信商户平台的重复支付风控规则或提示文案。
- 改造支付宝、余额充值等非本故障链路的业务流程。
- 自动上传/发布微信小程序体验版；发布和真机扣款验证需要单独确认。

## Decisions

- 支付结果短时无法确认时，锁定二次支付并继续有限查单/稍后恢复；重复扣款安全优先于立即重试速度。
- 采用前端状态机与后端旧交易预检双重防线，不只修补单个页面提示。
