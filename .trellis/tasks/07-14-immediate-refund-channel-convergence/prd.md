# 修复支付成功后立即退款渠道确认竞态

## Goal

用户完成微信小程序虚拟支付后，应能立即从服务订单详情提交退款申请；系统必须在退款决策前主动收口支付渠道分类，不得把内部定时补偿窗口暴露为“请稍后重试”，同时不得把 iOS Apple 订单误送入开发者主动退款接口。

## Background and Confirmed Facts

- 报错唯一来源为 `yoshop2.0/app/common/service/order/Refund.php:175-180`：成功虚拟交易的 `channel_class=UNKNOWN` 时，本地主动拒绝退款，微信退款 API 尚未被调用。
- 支付成功事实与支付渠道分类是两个独立事实。微信 `xpay_goods_deliver_notify` 足以触发订单支付成功，但真实通知报文不包含 `order_type`，不能完成 `NON_IOS / IOS_APPLE` 分类。
- `yoshop2.0/app/api/service/cashier/Payment.php:1138-1141` 在本地订单已支付时直接返回，导致客户端支付后查单跳过微信 `query_order`，错失立即获得 `order_type` 的机会。
- 当前定时任务会查询 `channel_class=UNKNOWN` 的已支付交易并完成分类，但调度延迟会让用户先看到退款错误。
- 生产订单 `10537` / 交易 `10363` 已完整复现：
  - `2026-07-14 21:16:43` 支付成功通知落库，交易成功但渠道为 `UNKNOWN`；
  - `21:16:59` 首次退款申请进入事务后因渠道未知回滚；
  - `21:17:22` 定时查单取得 `order_type=0`，分类为 `NON_IOS`；
  - `21:18:27` 用户重试成功发起退款，`21:18:39` 收到退款成功通知。
- `order_type=0` 是有效的非 iOS 证据，不能按空值或 truthy 语义丢弃。
- 当前工作区包含多个未提交任务的共享改动；不得回退、覆盖或整体提交无关修改。

## First-Principles Invariants

1. **资金事实和渠道事实分别收口**：订单已支付不能作为跳过渠道分类的条件。
2. **退款路由必须先有渠道证据**：`NON_IOS` 才能调用开发者退款；`IOS_APPLE` 必须进入 App Store 流程；`UNKNOWN` 必须安全失败。
3. **边界主动收口**：支付完成边界和退款入口都应主动查单，不应依赖用户重试或等待定时任务。
4. **外部网络不进入退款数据库锁区间**：渠道预查应发生在创建退款单的事务之前；事务内仍重新读取并验证最终交易。
5. **未知不产生半成品**：查单失败或仍无分类证据时，不创建退款单、不调用退款 API、不改变订单风险或服务状态。
6. **已知渠道不重复查单**：已经分类的交易沿用现有 Android、非 Apple 和 iOS Apple 流程。

## Requirements

### R1 — 支付完成时补齐渠道收口

- 虚拟支付主动查单仅在“本地订单已支付且渠道已分类”时快速返回。
- 本地订单已支付但交易渠道仍为 `UNKNOWN` 时，继续调用微信 `query_order` 并持久化结果。
- 查单得到 `order_type` 后必须通过既有单调分类逻辑更新 `channel_class`。
- 对已支付订单再次执行支付成功服务必须保持幂等，不得重复扣减库存、累计消费或创建交易。

### R2 — 退款入口同步预查

- 用户打开退款申请页或直接提交退款时，若最终虚拟交易已支付但渠道仍为 `UNKNOWN`，服务端应在退款事务外执行一次微信查单。
- 预查结果必须写入交易快照并刷新持久化渠道分类，再由现有退款投影和事务读取最新分类。
- `NON_IOS` 继续现有开发者退款流程；`IOS_APPLE` 继续现有 App Store 引导、不可逆冻结和审核流程。
- 查询错误、返回结构异常或仍无 `order_type` 时保持 `UNKNOWN` 并安全拒绝，不得猜测为非 iOS。

### R3 — 兼容与可观测性

- 普通微信支付、支付宝、余额支付及已分类虚拟支付行为不变。
- 不修改微信退款金额、退款单号、通知收口和 iOS 风险状态机语义。
- 记录不含密钥、access token、完整 session 或敏感签名的渠道预查结果日志。
- 保留定时补偿作为最终兜底，但正常立即退款不得依赖它。

## Acceptance Criteria

- [x] AC1：本地订单已支付、虚拟交易成功且 `channel_class=UNKNOWN` 时，收银台 `tradeQuery` 不提前返回，并通过微信查单完成分类。
- [x] AC2：相同状态下用户首次进入/提交退款即可在事务外完成渠道预查；若微信返回 `order_type=0`，同一次用户操作直接进入现有非 iOS 退款流程。
- [x] AC3：微信返回 `order_type=7` 时，同一次操作进入 iOS Apple 退款流程，绝不调用开发者 `refund_order`。
- [x] AC4：微信查单失败、结构异常或无渠道证据时，不创建退款单、不改变订单/交易/风险状态，并返回安全且可理解的错误。
- [x] AC5：已知 `NON_IOS / IOS_APPLE` 的交易不增加额外渠道预查；非虚拟支付路径不变。
- [x] AC6：支付成功、退款申请和退款通知的既有幂等与并发测试继续通过。
- [x] AC7：新增回归测试覆盖“已支付不能跳过未知渠道收口”和“退款事务前预查”契约；相关 PHP lint、合同测试与本地虚拟支付 E2E 通过。
- [x] AC8：共享文件的 diff 经逐段复核，无任何无关任务改动被回退或覆盖。

## Out of Scope

- 不缩短或移除定时任务调度周期。
- 不改变 Apple 最终退款决策、商家审核或服务冻结规则。
- 不增加前端自动重试、退款队列、消息队列、后台 worker 或新的数据库字段。
- 不发布小程序体验版、不部署后端、不执行新的真实付款或真实退款。
