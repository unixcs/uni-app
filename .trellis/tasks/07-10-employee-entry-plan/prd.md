# 游戏护航小程序员工入口规划

## 1. Goal / User Value

在当前 **游戏护航小程序** 中新增一个“正规包装”的 **员工入口**，让商家员工（对外展示为正式员工/服务人员，而不是直接暴露“打手”概念）能够进入独立的员工侧工作流；同时 **最大化复用现有服务订单、退款、订单详情、商家后台服务动作能力**，避免为了参考文档而额外复制一整套新系统。

### 问题重述（第一性原理）
真正要解决的问题不是“照着参考 PRD 新造 18 个接口和一整套员工系统”，而是：

> 在不破坏现有小程序购物/下单链路的前提下，为已有的游戏服务订单补上一条 **员工身份入口 + 员工侧操作闭环**，让服务执行权从纯后台操作扩展到小程序端可控。

### 基本原则（奥卡姆剃刀）
1. **先复用现有订单事实，再补员工身份。** 订单、退款、服务开始/完成能力已存在时，不重复造轮子。
2. **先做必要闭环，再做扩展后台。** 如果 MVP 只需员工入口、身份、接单/开始/完成，就不要提前引入邀请码、批量结算、复杂审核批次等次级系统。
3. **包装正规，不改业务本质。** 前台文案、入口、权限应体现“员工中心/服务人员中心”，底层仍服务于现有游戏护航订单流。

## 3. Reference-Only Intent from `/opt/yoshop/员工系统prd.md`

以下内容仅作为“业务思路参考”，**不能直接等同于当前项目实现范围**：

1. 在小程序“我的”页新增员工入口。
2. 员工需有独立身份，不应与普通 C 端购物身份混淆。
3. 员工侧核心动作围绕：
   - 接单/抢单
   - 开始服务
   - 完成服务
   - 收益/结算查看
4. 商家侧仍保留审核、退款、结算、入口开关等总控权。

## 4. Requirements (Current Planning Draft)

### R1. 员工入口必须挂载在当前小程序已有信息架构内
- 默认首选放在 `pages/user/index.vue` 的“我的服务”区域，而不是新造一个脱离现有导航的壳页面。
- 文案应包装为 **员工中心 / 服务人员中心 / 专属服务入口** 一类正式名称，避免前台直接暴露“打手中心”带来的审核/品牌风险。

### R2. 员工能力必须建立在“复用现有 user_id + 独立员工角色 + 权限隔离”之上
- 员工不是简单复用普通用户订单页按钮。
- 身份模型确定为：**先走现有小程序登录，再在当前 `user_id` 上扩展 employee profile / role / audit status 等员工事实。**
- 至少要区分：
  - 普通下单用户视角
  - 员工执行服务视角
  - 商家后台管理视角
- 员工只应看到自己有权操作的员工页、员工订单、员工收益，不应天然继承后台管理权限。
- 员工登录入口的体验可以独立包装，但底层会复用现有 `userId + token` 登录态，而不是新增第二套登录票据体系。

### R3. 订单主链路应优先复用现有服务订单事实模型
- 不重新发明订单主表、退款主表、服务单字段结构。
- 优先基于现有：
  - 服务单识别
  - 订单状态
  - 退款状态
  - 商家后台的开始/完成服务动作
- 如需新增员工接单归属，应该是在现有订单事实上增加“员工归属/服务执行态”，而不是分叉出第二套订单体系。

### R4. 第一阶段必须至少形成一个可闭环的员工端作业流
最小闭环至少要回答：
1. 员工如何进入？
2. 员工如何证明身份？
3. 员工看到什么订单？
4. 员工如何接单/认领？
5. 员工如何开始服务？
6. 员工如何完成服务？
7. 用户退款与商家退款时，员工侧数据如何同步失效或回收？

### R5. 商家仍需保留总控能力
参考文档中的核心思想可保留为规划原则：
- 入口显隐最好由商家配置控制；
- 商家保留审核权；
- 商家保留最终退款权；
- 员工侧只承接执行动作，不承接最终资金出款动作。

### R6. 首期按“完整一期”规划，不再按轻量 MVP 收缩
根据用户最新确认，首期不只是入口和员工端订单按钮，而是要按参考 PRD 的**完整业务思路**来规划，但实现方式仍必须基于当前项目现实：
- 纳入首期规划的模块包括：
  - 员工入口显隐
  - 员工注册 / 登录 / 审核
  - 邀请码或准入机制
  - 订单池 / 抢单
  - 开始服务 / 完成服务
  - 商家退款总控与员工侧状态回收
  - 收益明细
  - 商家结算批次 / 打款确认
- 但即便按完整一期规划，也仍需坚持：
  - 尽量复用现有小程序登录、订单、退款、后台服务动作能力
  - 不照搬参考文档中的接口命名和字段，实际参数以当前项目为准
  - 只有当现有能力无法承接时，才新增独立模块或新接口

### R7. 员工准入方式确定为“小程序自助申请 + 邀请码/审核”
- 员工先以现有小程序用户身份登录，再进入员工入口发起申请。
- 员工角色的获得不是后台直接静默指派，而是经过：
  1. 用户提交员工申请
  2. 填写邀请码或准入凭证
  3. 商家审核通过 / 驳回
  4. 通过后解锁员工侧页面与订单能力
- 该路径意味着首期必须补齐：
  - 员工申请表单
  - 审核状态机（待审核 / 已通过 / 已驳回）
  - 员工入口的未开通态提示页
  - 审核后台入口与基础审核动作

## 5. Technical Notes / Simplification Direction

### 5.1 最小可行架构倾向
基于当前项目事实，最自然的简化路线是：

1. **先加员工入口与员工身份体系**
2. **复用现有服务订单与退款模型**
3. **把商家后台已有“开始服务 / 完成服务”能力抽到员工侧可调用的安全接口**
4. **补齐审核、邀请码、收益、结算等完整一期模块，但仍按最小增量拆解实现**

### 5.2 当前最值得避免的过度设计
- 直接照搬参考 PRD 的 18 个接口
- 为员工侧单独复制一份订单详情/退款主链路
- 一开始就做完整提现/自动打款
- 一开始就做过重的报表、趋势图、复杂筛选

### 5.3 当前最可能新增的新域事实
即使强复用现有体系，仍大概率需要新增以下事实层：
- 员工实体（身份、状态、审核状态、展示名等）
- 员工与订单的归属关系
- 员工可操作状态机（待接/已接/服务中/已完成/已失效）
- 员工收益/结算记录（如果首期纳入）

## 6. Out of Scope (Tentative)

以下内容目前先视为 **默认不直接承诺进入首版**，除非用户后续明确要求：
- 自动分单、复杂派单策略
- 小程序内提现
- 自动打款
- 高级 BI 看板/趋势图
- 多级审核、多角色审批链
- 与当前项目无关的新商城会员体系重构

## 8. Decisions Already Confirmed

1. **首期范围边界**：按 **完整一期** 规划，不只做 MVP。也就是说，规划中需要覆盖入口、身份、审核、准入、抢单、服务动作、退款联动、收益、结算等完整业务链，但技术实现仍遵循当前项目最小增量原则。

2. **身份模型**：复用当前小程序用户身份，不新建独立员工账号体系。也就是说，员工是基于现有 `user_id` 追加出来的角色/资料扩展，而不是再做一套手机号+密码+独立 token 的员工登录系统。

3. **员工准入路径**：采用 **小程序自助申请 + 邀请码/审核**。也就是说，用户先走现有小程序登录，再进入员工入口提交申请；商家审核通过后，当前 `user_id` 才获得员工侧权限。
