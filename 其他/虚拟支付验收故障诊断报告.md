# 微信虚拟支付验收故障诊断报告

- 诊断日期：2026-07-02
- 故障现象（用户实测）：
  - 图1：安卓手机微信扫描「开发者工具中小程序生成的虚拟支付二维码」，手机端弹出「系统繁忙，请稍后再试」
  - 图2：电脑端微信开发者工具中小程序界面随后弹出「requestVirtualPayment:fail automator capture only」
- 诊断范围：仅排查、只读，未修改任何代码

---

## 一、结论（TL;DR）

**这不是虚拟支付代码、签名、配置的 bug，是测试环境被自动化桩函数污染了。**

直接根因：当前微信开发者工具里运行的小程序，仍处于 `miniprogram-automator` 的 `mockWxMethod('requestVirtualPayment')` 劫持态（即项目内文档所称的「automator capture only 抓参态」）。被劫持后：

- 开发者工具侧：`wx.requestVirtualPayment` 调用被桩函数拦截，桩函数**直接 fail**，返回固定字符串 `requestVirtualPayment:fail automator capture only`，**根本不向微信支付系统发任何请求**。
- 手机侧：由于开发者工具侧没有发起真实支付请求，手机微信扫到的支付上下文无效（或为残留/过期二维码），微信服务端返回通用兜底「系统繁忙」。

两个报错是同一个根因的两侧表现，不是两个独立问题。

修复方向只有一条：**彻底退出 automator 模式，用普通 `cli open` 重新打开项目后再扫码支付。** 详见第五节。

---

## 二、第一性原理拆解

### 2.1 微信虚拟支付的支付发生在哪一层

微信虚拟支付（米大师 xpay）是一个 **JSAPI**：`wx.requestVirtualPayment`。它必须由小程序的 JS 运行时主动调用，再由微信宿主（小程序容器）拉起支付。它**不是**「后端生成一个支付二维码、用户拿手机去扫」的普通 Native 支付形态。

在开发者工具里做沙箱联调时，合法的真机调试路径是：
1. 开发者工具里小程序调用 `wx.requestVirtualPayment(params)`
2. 开发者工具无法直接在 PC 拉起虚拟支付，于是生成一个真机调试二维码
3. 安卓手机微信扫码，由手机微信向微信沙箱发起真实虚拟支付
4. 手机端完成支付，开发者工具侧 `success/fail` 回调被触发

**用户当前采用的「开发者工具生成二维码 + 安卓手机微信扫码」方式本身是对的**（项目文档 `虚拟支付/测试参考.md:18-20` 与 `虚拟支付/虚拟支付api.md:54-56` 都认可 Android 真机 + env=1 沙箱这条验收路径）。问题不在验收方式，在于运行时被污染。

### 2.2 「automator capture only」到底是什么

`miniprogram-automator` 提供一个能力：`miniProgram.mockWxMethod('requestVirtualPayment', fn)`，可以把小程序里的某个 `wx.*` API 替换成测试桩。项目自己的抓参文档 `虚拟支付/wx.requestVirtualPayment.md:118-136` 记录了这个桩的实现：

```js
await miniProgram.mockWxMethod('requestVirtualPayment', function (options) {
  // 仅记录参数，不发起真实支付
  captureVirtualPaymentArgs({ mode, signData, paySig, signature })
  if (typeof options.fail === 'function') {
    options.fail({ errMsg: 'requestVirtualPayment:fail automator capture only' })
  }
  return { errMsg: 'requestVirtualPayment:fail automator capture only' }
})
```

注意这个桩的语义：**只抓参、不支付、直接 fail**，fail 信息写死成 `automator capture only`。这是**项目自己定义的测试占位文案**，微信官方 API 词典里没有这个字符串。

所以这个字符串出现在开发者工具里，等同于一个铁证：当前小程序运行时里的 `wx.requestVirtualPayment` 已经被替换成了上面这个桩，调用它必然立即失败，不可能拉起真实支付。

### 2.3 为什么 automator 桩一旦注入会「粘住」

`mockWxMethod` 的注入是绑定在 **automator 持有的那个开发者工具会话**上的。只要这个 automator 会话不显式 `close()`，开发者工具进程不被重启，这个 mock 就一直生效——哪怕你之后是「手动点支付」而不是「脚本点支付」，调用走的还是同一个被劫持的运行时。

项目历史记录 `openspec/.../tasks.md:146` 原话：

> The same Windows-side mirror had an older `run-wechat-virtual-sandbox-e2e.cjs` that lacked the new automator-session cleanup/reopen logic. That meant a prior `cli auto` run could leave the operator's later manual payment attempt stuck in the `automator capture only` capture path even after the main workspace script had been fixed.

这正是当前故障的复刻：一次未清理干净的 `cli auto` 抓参会话，让之后所有手动支付都卡在 capture only 态。

项目备忘 `虚拟支付/虚拟支付api.md:58` 也反复强调：

> 自动化脚本若通过「微信开发者工具 cli auto」拉起项目，结束后必须显式退出 automator 模式，再用普通 `open` 重新打开项目；否则后续手动点击支付也会被留在 `capture only` 态。

## 三、为什么能排除「虚拟支付代码/签名/配置出错」

逐层验证，全部正常，故障与业务代码无关：

### 3.1 前端运行时实现正确
`yoshop2.0-uniapp/core/payment/wechat.js:44-84`，`paymentAsWxMpVirtual` 只把 4 个字段透传给 `wx.requestVirtualPayment`：

```js
wx.requestVirtualPayment({
  signData: options.signData,
  paySig: options.paySig,
  signature: options.signature,
  mode: options.mode,
  success(...) { resolve(...) },
  fail: res => reject(res)
})
```

通读全文，**运行时代码里没有任何位置注入 `automator capture only`**。这个字符串只出现在测试文档的 mock 示例里。

### 3.2 后端签名与参数生成正确且完整
`yoshop2.0/app/api/service/cashier/Payment.php:283-331`，`virtualUnifiedorder`：

- `signData` 含 `offerId/buyQuantity/env/currencyType/productId/goodsPrice/outTradeNo/attach`，符合契约 `references/virtual-payment-api-contract.md:1-32`
- `paySig = hash_hmac('sha256', 'requestVirtualPayment&' + signData, appKey)`，与文档 `wx.requestVirtualPayment.md:61-63` 一致
- `signature = hash_hmac('sha256', signData, session_key)`，一致
- env=1 时取沙箱 AppKey，env=0 时取现网 AppKey（`Payment.php:307-309`）
- 还会先用本次 `wx.login` 的 `loginCode` 刷新 `session_key`（`Payment.php:412-463`），避免旧登录态导致 signature 失效——这是项目专门修过的点

### 3.3 服务端查单/退款/履约签名正确
`app/common/library/wechat/VirtualPayment.php:65-73`，`signedPost` 用 `hash_hmac('sha256', uri + '&' + body, appKey)`，符合微信 `pay_sig` 规范。

### 3.4 沙箱 readiness 本地全绿
最近一次 readiness 证据 `runtime/virtual-payment-sandbox-check-after-automator-cleanup/sandbox-check-20260702164036.json`：

```json
"summary": { "ready": true, "failures": 0, "warnings": 0 }
```

逐项核对全部 ok：`enabled=1`、`env=1`、`offer_id=1450568898`、`sandbox_app_key` 已配、`merchant_id=1747296516`、`notify_base_url=https://wx.oiob.cn`、`message_push_token` 已配、`app_id=wxbf57e6f2ba72b712`、商品 10001 `vp_enabled=1/vp_product_id=vip0/vp_price_snapshot=1`、测试用户 `oauth_id` 与 `session_key` 均存在、通知入口文件与路由存在。

如果故障是签名或配置错误，readiness 不会全绿，而且报错会是 `-15005`、签名校验失败之类**微信侧的具体错误码**，绝不会是 `automator capture only` 这个测试桩文案。

### 3.5 iOS 限制不是本次原因
沙箱 env=1 确实不支持 iOS（`虚拟支付/虚拟支付api.md:52-56`、tasks.md:130），但用户明确用的是**安卓手机**，此限制不适用。且前端已被要求移除 iOS 预阻断（tasks.md:142-143），实测 `wechat.js` 确实没有 iOS/env 判定分支，不会误杀安卓。

## 五、立即验证步骤（只读，不改代码）

按顺序执行，目的是用排除法坐实根因。每一步都是只读/环境操作。

### 步骤 1：确认开发者工具当前是否挂在 automator 模式
- 打开开发者工具 → 右上角「设置 → 安全设置」，看「CLI/HTTP 调用」是否处于开启态（automator 必须开这个）。
- 若开了，先怀疑 automator 仍连着。

### 步骤 2：彻底重启开发者工具（关键）
1. 完全关闭微信开发者工具进程（不只是关窗口，要退出进程）。
2. 检查是否有遗留的 automator / `cli auto` 进程在后台（任务管理器看是否有 node 进程挂着 miniprogram-automator）。
3. **不要**用 `cli auto`、也不要用任何 `run-wechat-virtual-sandbox-e2e.cjs` 重新打开项目。
4. 用**普通方式**打开项目：
   - 手动双击开发者工具打开，或
   - `cli open --project <mp-weixin 产物目录>`（普通 open，非 auto）

### 步骤 3：确认 Windows 镜像项目用的是清理过的脚本
项目根 `虚拟支付/虚拟支付api.md:59` 与 tasks.md:145-147 反复出现一个坑：开发者工具实际打开的是 Windows 镜像项目 `D:\Program\0\home\0\yoshop1\yoshop2.0-uniapp`，而镜像里的 `scripts/run-wechat-virtual-sandbox-e2e.cjs` 可能是**缺 automator 清理逻辑的旧版**。若你之前跑过镜像里的旧脚本，必须确认镜像源码已和主工作区同步（tasks.md:147 记录的修复点：脚本应含 `shouldReopenManualDevtools`、`restoreManualDevtoolsSession()`、`await miniProgram.close()`）。

### 步骤 4：干净环境下重新扫码支付
完成步骤 2 后，在普通 open 的会话里重新下单 → 点支付 → 用安卓手机微信扫码。
- 若「automator capture only」消失、手机端能正常拉起 0.01 元沙箱支付 → 根因坐实，就是 automator 污染。
- 若仍出现该文案 → 说明 automator 没清干净，回到步骤 2 确认进程是否真的退出。

### 步骤 5：支付成功后落证据（对应 tasks 11.1）
用真实 `outTradeNo` 跑审计，把 11.1/11.8/11.9 收口：
```bash
cd /opt/yoshop/yoshop2.0
php think virtual-payment:sandbox-check \
  --goods-id 10001 \
  --user-mobile 19900000000 \
  --out-trade-no "<真实 outTradeNo>" \
  --expect-paid --expect-pending-contact \
  --expect-duplicate-notify --expect-query-evidence \
  --expect-no-duplicate-refund --expect-provide-goods-idempotent \
  --evidence-dir "/opt/yoshop/runtime/virtual-payment-sandbox-accept-final"
```

## 六、根除建议（后续可做，本次不改）

1. **抓参脚本与验收脚本彻底物理隔离**：抓参用的 `mockWxMethod` 脚本执行完，强制 `miniProgram.close()` 并退出 automator；建议在脚本 finally 块里保证 close，无论成功失败。
2. **加自检**：在手动支付前，用一段无害代码探测 `wx.requestVirtualPayment` 是否被 mock（例如检查 `wx.requestVirtualPayment.toString()` 是否含 native 特征），被劫持时直接提示「请退出开发者工具重开」，避免再误判为业务故障。
3. **镜像一致性硬校验**：tasks.md:153 已让 `build-mp-weixin.cjs` / `run-wechat-virtual-sandbox-e2e.cjs` 对 workspace、Windows 镜像、编译产物三处 `config.js` 的 `apiUrl` 做强一致校验并 fail fast；建议把同样的强校验扩展到「脚本本身是否含 automator 清理逻辑」，防止镜像又回退到旧脚本。
4. **文档措辞统一**：把 `automator capture only` 在所有文档里标注为「测试桩文案，出现即代表环境被自动化污染，禁止当作支付失败业务证据」，避免后续再次把它当真去查签名。

## 八、一句话回答用户
