## 二、问题描述

本地已成功接入 `wx.requestVirtualPayment`。

当前现象不是本地下单失败，也不是签名报错，而是：

1. 小程序前端成功拿到虚拟支付参数
2. 服务端成功记录 `wechat_virtual` 交易
3. 微信远端成功创建虚拟支付订单
4. 但微信远端很快将订单关闭，`xpay/query_order` 返回 `status=6`

这导致最终支付无法完成。

该现象已经在 **Windows trial** 和 **Android trial** 两条路径上复现，不是单一宿主问题。

## 四、我们已确认的本地结论

### 1. 配置参数已核对通过

已核对并确认以下参数在本地运行时一致：

- AppID
- OfferID
- 沙箱 AppKey
- 现网 AppKey
- 虚拟支付商户号
- 虚拟商品 `productId`
- 沙箱 / 现网环境 ID

本地沙箱就绪检查已通过。

### 2. 虚拟支付账户接口可用

使用当前 `AppID + AppSecret + 沙箱 AppKey` 直接调用微信虚拟支付接口：

- `stable_token` 获取成功
- `xpay/query_biz_balance` 返回 `errcode=0`

说明：

- 当前小程序 `AppID/AppSecret` 可用
- 当前虚拟支付账户可正常响应微信接口
- 当前 AppKey 可用于微信虚拟支付服务端签名

### 3. 本地代码链路已确认走的是虚拟支付，不是普通微信支付

最新失败交易在本地交易表中明确记录为：

- `platform=wechat_virtual`
- `env=1`
- `product_id=vip0` / `vip9`

说明当前失败不是普通微信支付串线。

### 4. 签名输入已核对

以交易号 `331838979039771611` 为例：

`signData` 为：

```json
{"offerId":"1450568898","buyQuantity":1,"env":1,"currencyType":"CNY","productId":"vip0","goodsPrice":1,"outTradeNo":"331838979039771611","attach":"331838967316195306"}
```

本地签名规则：

- `paySig = HMAC_SHA256(appKey, "requestVirtualPayment&" + signData)`
- `signature = HMAC_SHA256(session_key, signData)`

服务端每次支付前都使用前端 `wx.login` 提供的 `loginCode` 在服务端刷新 `session_key`，而不是从前端透传缓存 `session_key`。

### 5. 已排除商城金额改价冲突

商城侧已做如下约束：

- 虚拟支付商品仅支持单商品立即购买
- 仅允许单规格
- 仅服务商品可启用
- 商城售价必须与平台价格快照一致
- 最终应付金额必须与 `vp_price_snapshot` 一致，否则直接拒绝支付

因此当前失败不是由于优惠券、积分、会员价、后台改价等复杂结算逻辑导致的金额不一致。

### 1. 社区案例中有价值的信息

#### A. 工单格式

`微信开放社区 2.md` 给出的技术工单格式比较完整，适合官方快速接手：

- 基本信息
- 问题描述
- 已排查项
- 复现数据
- 请求协助

本草案已参考这一格式组织。

#### B. `session_key` 问题是真实高频坑

`微信开放社区 3.md` 中，作者最终定位到：

- 不是 HMAC 算法本身错
- 而是前端来回传递 `session_key`，导致签名虽然“算得对”，但使用的并不是微信当前认可的有效 `session_key`

这个结论对我们有参考价值，但经核对，**和当前项目不一致**：

- 当前项目不会让前端直接透传 `session_key`
- 当前项目支付前优先使用 `loginCode -> code2session` 在服务端刷新 `session_key`
- 刷新后会回写到用户 OAuth 记录和 token 缓存

因此，社区案例 3 的根因已经被当前项目规避，不是当前问题的主因。

#### C. 社区接入指引再次确认了签名算法和参数来源

`微信开放社区 1.md` 中对以下点的描述与当前项目一致：

- `paySig` 以 `appKey` 计算
- `signature` 以 `session_key` 计算
- `requestVirtualPayment` 的 `uri` 固定为 `requestVirtualPayment`
- `AppID / OfferID / AppKey` 来源于虚拟支付后台基础配置

这进一步支持当前本地签名实现方向无偏差。

### 2. 社区案例中暂未给出可直接修复当前问题的新思路

当前社区三篇材料里，真正能落到当前案子的只有两类：

1. 工单如何写得更容易被官方接手
2. `session_key` 是否用错

而我们当前案子的核心现象已经是：

- 微信远端订单存在
- 但远端状态为 `status=6`

这和 `SIGNATURE_INVALID`、`session_key` 失效不是同一层问题。
