## 三、关键修正①：实际脚本 ≠ v1 引用的桩

这是本次复查最重要的发现，直接削弱 v1 的证据链。

### v1 说的
> 脚本 `run-wechat-virtual-sandbox-e2e.cjs` 用 `mockWxMethod` 把 `wx.requestVirtualPayment` 替换成「直接 fail + 返回 automator capture only」的桩，所以运行时被劫持。

### 实际情况
聚焦 grep `yoshop2.0-uniapp/scripts/` 全目录：`capture only` / `mockWxMethod` / `mockMethod` / `restoreWxMethod` **全部零匹配**。

实际脚本 `run-wechat-virtual-sandbox-e2e.cjs` 用的是 **observer 转发模式**，不是 mock 拦截模式：
- `installVirtualPaymentObserver`（脚本内约 483-528 行）：保存 `const original = wx.requestVirtualPayment`，重写为「先记录参数、再 `original.call(this, …)` 转发真实调用」。
- 关键区别：**它不 fail、不吞掉调用，而是把参数透传给真实支付**。

### 这意味着什么
产生 `automator capture only` 的，**不是当前这个脚本**，而是 `wx.requestVirtualPayment.md:118-132` 描述的那个「旧版/示例」mock 桩。两者是**不同的实现**：
- 文档示例桩：mock + fail + 返回固定文案（产生 automator capture only）
- 实际脚本：observer + 转发（不产生该文案，能拉起真实支付）

所以 v1「脚本 mock 桩劫持了运行时」这句话**描述错了对象**。正确表述应是：**只有当某个会话用了文档示例那种 mock 桩（或旧版含该桩的脚本）且未清理，才会出现这个错误。**

`tasks.md:146` 印证了这个分歧：历史上 Windows 镜像里曾存在「缺 automator 清理逻辑的旧脚本」，残留的 automator 会话会让后续手动支付卡在 capture only。v1 把「历史问题」当成「当前脚本行为」描述了。

## 四、关键修正②：sandbox-check 是本地静态校验，不是联网真验

### v1 的过度断言
> 沙箱 readiness 全绿（`summary.ready=true, failures=0`）⇒「配置/签名/商品/用户全部就绪」

### 实际能力边界
聚焦审查 `yoshop2.0/app/common/command/VirtualPaymentSandboxCheck.php`：全文**没有任何** `curl_exec` / `httpPost` / `->send(` / `api.weixin.qq.com` / `xpay` 调用。它是**纯本地校验**：
- 查 DB：商品 `vp_enabled/vp_product_id/vp_price_snapshot`、测试用户 `oauth_id/session_key`、是否已有 `wechat_virtual` 真实成交单
- 查 config：`enabled/env/offer_id/sandbox_app_key/merchant_id/notify_base_url/message_push_token/app_id`
- 查文件：通知入口 `public/notice/virtualPayment.php` 是否存在

它**完全无法证明**：
- ❌ AppKey 是否正确（只校验「非空」，不校验「配对了正确的商户」）
- ❌ `paySig`/`signature` 算法是否能通过微信服务端校验（不发请求）
- ❌ `offerId` 是否绑定到当前 AppID（不联网）
- ❌ 测试用户 `session_key` 是否还在有效期（微信 session_key 有时效，可能已过期）
- ❌ `notify_base_url` 是否真能被微信回调到达（只校验字符串格式）

### 结论修正
「readiness 全绿」只能说明**本地静态前置条件齐了**，**不能**作为「签名/配置必然正确」的证据。v1 用它排除业务故障是**逻辑越界**。真实支付能否成功，必须靠真实沙箱成交来证明——而 11.1/11.8/11.9 至今 pending（`tasks.md:83,90,91`），说明**从未有过一笔真实沙箱成功单**。

## 五、关键修正③：手机端「系统繁忙」的因果链存在断点

### v1 的因果链
> PC 端被桩直接 fail、不向微信发请求 ⇒ 手机端扫到无效/残留二维码 ⇒ 微信返回「系统繁忙」

### 这里讲不通的地方（第一性原理碰撞）
如果 PC 端 `wx.requestVirtualPayment` 被 mock 桩**同步直接 fail**（`options.fail(...)` 是同步调用），那么：
- 这通调用在 PC 端小程序运行时就结束了，**根本不会生成给手机扫的真机调试二维码**。
- 手机如果扫到二维码，那张二维码要么是**更早某次成功发起的真实支付**生成的，要么是**开发者工具的真机调试入口二维码**（与具体某次 JSAPI 调用无关）。

也就是说：**「PC 端被桩 fail」和「手机端弹出系统繁忙」之间，没有必然的同步因果关系。** 把两者强行用「连带结果」连起来，是 v1 的逻辑跳跃。

### 更严谨的两种解释
两个症状**可能同源、也可能异源**，必须分开看：

**解释 A（同源·automator 残留，v1 的方向，但需补全）：**
开发者工具的真机调试通道本身被一个未关闭的 automator 会话占用/锁死。手机扫码进入的真机调试会话，其小程序运行时也加载了同一个被 mock 的 `wx.*`（因为真机调试时小程序逻辑跑在开发者工具侧的 JS 引擎里，mock 对真机调试同样生效）。手机侧「系统繁忙」可能是开发者工具把 fail 结果回传给手机端时、手机微信做兜底翻译产生的通用文案。**这条链路成立的前提是：手机扫码进入的是「真机调试」模式，且该模式下 mock 仍生效。** 需要用户确认扫码后手机是「进入真机调试」还是「直接拉起微信支付」。

**解释 B（异源·真实支付失败，v1 完全没考虑）：**
- PC 端文案：来自某次未清理的 mock 桩（与 v1 一致）
- 手机端「系统繁忙」：来自一次**真实的、签名错误的**支付请求失败

「系统繁忙」是微信极其通用的兜底文案，在虚拟支付场景下，签名错误（paySig/signature 校验失败）、offerId 与 AppID 不匹配、session_key 过期、AppKey 用错环境（沙箱/现网混淆）都可能被翻译成「系统繁忙」而非具体错误码。**由于从未有过真实成功单（11.1 pending），我们不能排除业务侧签名/配置在真实联网时其实是不通的。**

## 八、最短可靠的验证路径（分两段，先排 automator 再排业务）

### 第一段：排 automator（最快，几分钟）
1. **完全杀掉**开发者工具进程 + 后台所有 node/miniprogram-automator 进程（任务管理器确认，不是关窗口）。
2. **不要**跑任何 `cli auto`、不要跑任何含 mock 的脚本。
3. 用**普通方式**打开项目：手动双击 DevTools 打开，或 `cli open --project <mp-weixin 产物目录>`。
4. 关键自检（可在小程序里临时加一段调试，或看控制台）：判断当前 `wx.requestVirtualPayment` 是否被替换——若被 mock，调用会同步立即 fail 并返回 `automator capture only`；若是 native，会进入支付流程（可能弹起拉起或返回 native 错误码）。
5. 重新下单 → 点支付 → 安卓扫码。

**分支判断：**
- 若「automator capture only」**消失** → 根因坐实是 automator 残留（解释 A）。但手机端若仍「系统繁忙」→ 进入第二段。
- 若「automator capture only」**仍在** → 当前 DevTools 会话不是 tasks.md:151 那个干净会话（悖论可能 1/2），需确认实际打开的项目路径和 build 时间。

### 第二段：排业务（仅当第一段清理后手机端仍「系统繁忙」）
此时 PC 端文案应该已经没了，剩下的「系统繁忙」是**真实支付失败**，按真实失败排查：
1. 抓后端 `virtualUnifiedorder` 实际下发的 `signData/paySig/signature`（用 observer 转发脚本抓，不要用 mock 桩）。
2. 核对 env：沙箱必须 env=1 + sandbox_app_key；现网 env=0 + app_key。两者 AppKey 不可混用。
3. 核对 `wx.login` → `session_key` 刷新是否真的成功（看后端日志，确认用的是**本次** login 的 key，不是缓存）。
4. 用抓到的参数手动 POST 微信沙箱下单接口，看返回的具体错误码（`-1/-15005/签名错误` 等），而不是泛化的「系统繁忙」。
5. 确认 `offerId=1450568898` 已在微信虚拟支付后台绑定到 `app_id=wxbf57e6f2ba72b712`。

## 九、本次复查发现的、v1 没提到的新风险

1. **sandbox-check 给了虚假的安全感。** 它全绿不代表真能付。建议给它加一个明确的输出标注：「本检查为本地静态前置校验，不验证签名/联网/绑定」。否则团队会反复拿「全绿」当业务无故障的证据（v1 就是被它误导了）。
2. **两套抓参方案并存是认知陷阱。** 文档里 mock+fail 桩（`wx.requestVirtualPayment.md`）与实际 observer 转发脚本（`run-wechat-virtual-sandbox-e2e.cjs`）是两套不同实现，但文档没显式标注「示例桩不可用于真实验收，请用 observer 脚本」。操作员很容易照文档示例跑 mock 桩然后忘记清理。建议文档加显式警告。
3. **从未有过真实成功单。** 11.1/11.8/11.9 一直 pending，意味着整个虚拟支付链路的「真实端到端成功」从未被证明过。当前所有「通过」都是本地 mock/本地 e2e。在第一笔真实沙箱成功之前，不能宣称接入完成。
4. **Windows 镜像漂移是反复发作的根因温床。** `tasks.md:145,153,155,164` 显示镜像 config.js、脚本、build 产物多次漂移又被修。只要 build 流程还能临时覆盖镜像 config，这类问题就会反复。建议把「镜像三处 config.js 强一致校验」做成 CI 硬门禁（tasks.md:153 已加，但要确保不被绕过）。
5. **mock 桩的清理不可靠。** 即便新脚本有 `miniProgram.close()`，只要 mock 桩是注入到「DevTools 会话」而非「脚本进程」的，脚本崩溃/异常退出时 close() 不一定执行。建议改用 `try/finally` 强制 close，并在脚本启动时先探测并清理可能存在的旧 mock。
