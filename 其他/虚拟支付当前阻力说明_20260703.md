# 微信虚拟支付当前阻力说明（2026-07-03）

## 目的

这份文档用于把当前 YoShop 小程序虚拟支付接入的真实状态、已验证事实、已排除方向、仍未收敛的外部阻力，一次性交给新的审查者或其他 AI 模型。

写法遵循“墨菲定律”思路：凡是可能出错的环节，都默认它可能已经出过错，因此不依赖单点结论，优先看证据链、时间线和已被反复证伪的方向。

---

## 一句话结论

当前仓库代码、配置、构建产物、Windows 镜像、OAuth 绑定、运行权限、服务单主链路、本地虚拟支付回归，都已经被修到一个相对干净的状态；**唯一还没有拿到的，是一笔真实 Android + 微信虚拟支付沙箱 `0.01` 支付成功证据**。

用户当前仍看到的：

- 安卓微信扫码后：`系统繁忙，请稍后再试`
- DevTools 小程序界面随后：`requestVirtualPayment:fail automator capture only`

这两个现象目前不能再简单视为“代码没接通”。更接近的判断是：

1. **真实后端链路已经能生成 `wechat_virtual` 交易，不是普通微信支付。**
2. **部分历史/当前 DevTools 弹窗很可能仍带有会话噪声，不一定对应一次新的真实支付尝试。**
3. **真正剩余的问题，卡在“真实客户端拉起后，微信远端为什么没有成功进入 paid 状态”这一层。**

## 目前最关键的第一性原理判断

### 判断 1：后端 `cashier/orderPay` 生成签名参数，不等于微信远端已经建单

对一个“仅后端生成、未经过客户端真实调用 `wx.requestVirtualPayment`”的交易做远端查询，返回：

- `errcode=268490002`
- `errmsg=数据不存在`

这说明：

- 后端 `orderPay` 只是生成 `signData/paySig/signature`
- 微信侧真正的 xpay 订单创建，发生在客户端真实调用 `wx.requestVirtualPayment` 之后

证据：
- `openspec/changes/add-mp-virtual-payment-service-orders/tasks.md:193`

### 判断 2：真实 Android 尝试里，微信远端曾经“认得这笔单”，但没有 paid

对较新的两笔真实 Android 尝试，远端查询返回：

- `errcode=0`
- `order.status=6`

这说明：

1. 那些尝试并不是“完全没打到微信远端”
2. 微信远端确实见过对应订单
3. 但它们没有进入本地期望的 paid 收敛

这比“代码根本没走通”更窄，也更棘手。

证据：
- `openspec/changes/add-mp-virtual-payment-service-orders/tasks.md:184`
- `openspec/changes/add-mp-virtual-payment-service-orders/tasks.md:185`
- `yoshop2.0/runtime/codex-evidence/virtual-payment-sandbox-audit-trade-10111-remote/sandbox-check-20260703121351.json`
- `yoshop2.0/runtime/codex-evidence/virtual-payment-sandbox-audit-trade-10116-remote/sandbox-check-20260703121544.json`

### 判断 3：当前的 `automator capture only` 不能再被直接等价成“本次支付真实失败根因”

最重要的最新证据是：

- 用户最近一次看到这个弹窗时，数据库里没有新交易产生

所以它更像：

- DevTools/automator 会话噪声
- 旧会话残留提示
- 或某个非真实支付链路的前端失败提示

而不是“这次新扫码支付触发了后端、后端又因为 automator 真失败”。

也就是说，**现在至少有两层现象被混在一起了**：

1. 真正的虚拟支付交易曾经创建成功，但远端停在 `status=6`
2. DevTools 仍可能不时弹出 `automator capture only`，而且不一定对应一笔新交易

## 目前仍未解决的核心问题

### 核心未解

**为什么真实 Android + DevTools 外部扫码链路下，微信虚拟支付远端最终没有给出 paid 结果？**

从目前证据看，真正尚未解释清楚的层次更接近下面几类：

1. 微信沙箱远端对当前签名/环境/offerId/session 组合的接受条件
2. `order.status=6` 在当前虚拟支付沙箱语义下的准确含义
3. DevTools 外部扫码与真实 `wx.requestVirtualPayment` 拉起之间，是否仍有会话级污染或设备侧限制
4. 是否存在微信侧测试账号、沙箱资格、offerId/appId/商户配置层面的外部约束

注意：这些点大多已经超出纯本地代码阅读能完全证明的范围。

## 墨菲定律视角下，接手审查时最容易踩的坑

### 坑 1：把 `automator capture only` 当成唯一根因

它很重要，但现在不能再单点定性。  
因为最新事实是：它有时甚至不对应新的真实交易。

### 坑 2：看到 readiness 全绿，就以为微信远端也没问题

readiness 只能说明本地前置条件齐了，**不能**证明微信远端一定接受并完成支付。

### 坑 3：忽略“曾经走普通支付”和“当前走虚拟支付”是两个不同阶段

如果不区分时间线，很容易把旧证据和新证据混在一起，得出错误结论。

### 坑 4：忽略 Windows 镜像、编译产物、DevTools 会话三者可能不同步

即使源码修了，也不代表用户手上 DevTools 当前运行的会话就是那份新构建。

### 坑 5：只盯本地代码，不看微信远端状态

当前最值钱的证据已经不是继续 grep 前端字符串，而是：

- 这次扫码有没有产生新 trade
- 远端 query 返回了什么
- 最终是 `数据不存在`、`status=6`，还是别的显式错误码

## 建议下一位 AI 或审查者优先接手的方向

### 优先级 1：把“新尝试”与“旧弹窗噪声”严格分离

不要再只盯界面文案。  
每次人工重试前，先用：

```bash
cd /opt/yoshop/yoshop2.0
php think virtual-payment:watch-live --goods-id=10001 --timeout-seconds=180 --settle-seconds=60 --probe-remote-query
```

然后再让操作者做一次真实安卓扫码支付。

这样可以第一时间回答：

1. 到底有没有产生新 `wechat_virtual` trade
2. 新 trade 的 `out_trade_no` 是多少
3. 远端 query 是 `数据不存在`、`status=6`，还是 paid
4. 本地 order/trade 是否进入 paid / 待联系

### 优先级 2：把微信远端 `status=6` 当成主线研究对象

目前最值得别的模型从外部文档、经验库、微信虚拟支付沙箱约束角度重点审查的是：

- `xpay/query_order` 返回 `status=6` 在当前场景下到底代表什么
- 它对应的是取消、拒付、签名不通过后的终态、测试账号不符合、还是其他沙箱限制

### 优先级 3：重新审视“测试账户/沙箱资格/offerId 绑定关系”

虽然本地配置已全绿，但仍建议新的审查者从外部规则角度重点看：

- 当前登录 DevTools 的账号、扫码支付账号、沙箱测试账号之间的关系
- offerId 与 appId、商户、虚拟支付后台资格之间是否还有隐藏约束
- Android 外部扫码路径是否要求更严格的测试身份一致性

### 优先级 4：把 DevTools 会话污染当作并行假设，而非唯一假设

可以继续怀疑 automator 残留，但不要只在这条线上打转。  
因为我们已经有证据表明：某些真实尝试确实打到了微信远端，只是没 paid。
