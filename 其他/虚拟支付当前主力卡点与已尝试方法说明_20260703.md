# 虚拟支付当前主力卡点与已尝试方法说明

更新日期：2026-07-03 23:00（Asia/Shanghai）

## 1. 当前结论

这不是一个“普通微信支付误接入”的问题，也不是一个“本地完全没走到虚拟支付”的问题。

截至目前，已经可以确认：

1. 后端确实在走微信虚拟支付链路，而不是普通微信支付。
2. 小程序下单后，服务端确实会生成真实的 `wechat_virtual` 交易。
3. 商品映射、`productId`、固定价格、`session_key`、`paySig/signature`、订单落库、查单工具链，当前都基本可用。
4. 真正的主力卡点已经收敛到：
   - 微信侧返回 `requestPayment:fail:access denied`
   - 或者微信远端 `xpay/query_order` 返回非成功状态，主要是 `status=6`
   - 个别最新单会先看到 `status=1`，但也没有收敛到已支付

也就是说，当前最像是“微信沙箱/体验版/测试账号/上游风控或资格限制”层面的阻断，而不是本地代码完全没接通。

## 2. 现在用户侧看到的典型报错

### 2.1 手机上的报错

- 安卓手机扫码或体验版下单后，常见提示：
  - `系统繁忙，请稍后再试`
  - `微信虚拟支付仍在处理中`
  - `requestPayment:fail:access denied`

### 2.2 微信开发者工具/控制台里的报错

- 早期常见：
  - `requestVirtualPayment:fail automator capture only`
- 后续常见：
  - `requestVirtualPayment:fail requestPayment:fail cancel`
  - `requestVirtualPayment:fail requestPayment:fail:access denied`
  - `Error: timeout`
- 最近补充日志里已经明确看到：
  - `WechatChannel pay fail > {errno: 102, errMsg: "requestPayment:fail:access denied"}`
  - `onPayFail > {errMsg: "requestVirtualPayment:fail requestPayment:fail:access denied", ...}`

### 2.3 一个已修掉的本地误报

曾经出现：

- `errCode: -15105`
- `iOS 端不支持虚拟支付沙箱环境，请改用 Android 真机测试，或切到现网环境后再验证`

这个报错后来确认是**前端本地误拦截**：

- DevTools 的 `platform=devtools`
- 但 `system` 里会带 iPhone/iOS 模拟信息
- 旧逻辑把它误当成“真 iPhone 宿主”，于是支付在弹二维码前就被本地挡掉了

这个问题已经修复，见第 6 节。

## 3. 当前最关键的第一性原理判断

从链路拆解来看，虚拟支付至少经过这几层：

1. 商品是否被识别为虚拟支付商品
2. 收银台是否走 `wx.requestVirtualPayment`
3. 服务端是否生成正确的 `signData/paySig/signature`
4. 服务端是否按 `wechat_virtual` 落交易
5. 客户端是否真正把这组参数提交给微信
6. 微信远端是否创建虚拟支付订单
7. 微信远端是否允许该订单完成支付并进入已支付态
8. 回调/查单是否把成功状态收敛回本地订单

目前 1 到 6 基本都已有证据成立。

真正卡在 7：

- 微信远端订单经常被关闭，或直接 `access denied`
- 没能进入“已支付”

## 4. 已经排除或基本排除的方向

## 4.1 不是普通微信支付误接入

早前确实发生过一次环境漂移：

- `goods_id=10001` 被改坏
  - `vp_enabled=0`
  - `vp_product_id=''`
  - `vp_price_snapshot=0`

那一阶段会退回普通微信支付，用户看到普通商户名，且虚拟支付后台查不到记录。

这个问题后来已经恢复：

- `goods_id=10001`
  - `vp_enabled=1`
  - `vp_product_id='vip0'`
  - `vp_price_snapshot=1`

恢复后，新的交易已重新证明走的是 `wechat_virtual`。

## 4.2 不是“商品没映射 productId”

当前映射有效：

- `10001` -> `vip0` -> `0.01`
- `10002` -> `vip9` -> `9.9`

并且后台有固定价格约束，避免普通改价链路污染虚拟支付。

## 4.3 不是签名链路完全没接通

已经有大量真实交易表明：

- 服务端完成了 `signData`
- 服务端完成了 `paySig`
- 服务端完成了 `signature`
- 小程序能拿到 `provider=virtual`, `platform=wechat_virtual`

如果签名链路完全断掉，通常不会稳定落出这么多真实虚拟支付交易。

## 4.4 不是 openid/session_key 完全缺失

当前测试用户 `user_id=10004` 的 `MP-WEIXIN` 绑定是有效的，且重复绑定问题已经做过清理。

最近一次表内状态：

- `id=10004`
- `user_id=10004`
- `oauth_type=MP-WEIXIN`
- `oauth_id=o1Wtm3eQK7SFsb_RVCKUToFS3ENo`
- `is_delete=0`

且在最新重试里，`session_key` 有刷新时间，说明这次支付并不是拿着一个空登录态在硬试。

## 4.5 不是“根本没走到微信远端建单”

已有多笔交易通过 `xpay/query_order` 查到微信远端确实存在订单，例如：

- `331566256851360090`：远端 `status=1`
- `331568606492532301`：远端 `status=6`
- `331568403486317667`：远端 `status=6`

这说明不是“本地自嗨”，而是微信远端真的接到了虚拟支付订单。

## 4.6 不是 DevTools 里完全没同步到新源码

这件事曾经是问题，但已经被识别并处理多次。

已做过：

- WSL 源码同步到 Windows 镜像目录
- 重建 `mp-weixin`
- 清理 DevTools 缓存
- 重开 DevTools
- 上传新的体验版

不过仍然要注意：HBuilderX CLI 编译并不稳定，存在“源码新、Windows 镜像新、但 `unpackage/dist/dev/mp-weixin` 还是旧产物”的风险。

## 5. 当前仍然最可疑的主力卡点

以下方向是当前最值得继续深挖的：

### 5.1 微信沙箱资格 / 体验成员 / 支付账号资格

现在最像的问题之一是：

- 下单的小程序登录身份
- 体验版/开发版身份
- 实际付款的安卓微信号
- 虚拟支付沙箱测试资格

这几者之间存在资格不匹配。

因为现在看到的核心错误已经越来越偏向：

- `access denied`
- 远端建单成功但很快关闭

这更像是微信侧权限/资格/风控层面的拒绝，而不是本地参数没传。

### 5.2 trial / develop / experience / preview 路径差异

已经确认过：

- DevTools 预览态会制造很多噪音
- `automator capture only` 曾经是 DevTools/automator 残留造成的假信号
- 后来已经改用体验版做分流验证

但即便体验版也仍出现：

- `requestPayment:fail:access denied`
- `status=6`

所以现在虽然不能只怪预览态，但运行环境差异仍需谨慎看待。

### 5.3 微信侧商品/沙箱治理策略

当前 `vip0` 和 `vip9` 都能建单，但都不能稳定成功。

表现为：

- `vip0` 有时 `status=1`
- `vip9` 多次 `status=6`
- 最新几笔又都收敛到 `status=6`

需要继续确认：

1. 这些 `productId` 是否在当前沙箱/体验链路下真实可付
2. 是否存在特定测试账号白名单限制
3. 是否存在 offerId/appId/productId 组合层面的限制

## 9. 建议下一位 AI 继续排查的优先顺序

建议按这个顺序继续：

1. 先承认：本地虚拟支付链路已经大体接通，不要再从“是不是普通微信支付”重新推倒。
2. 优先深挖微信侧资格与环境问题：
   - 当前登录小程序账号
   - 当前体验成员资格
   - 当前付款安卓微信号
   - 当前虚拟支付沙箱测试资格
   - 当前体验版/开发版/预览版差异
3. 对比 `vip0` 与 `vip9` 的微信后台配置差异，确认是否存在商品级限制。
4. 如果继续重试，第一时间审计最新 `out_trade_no`，看远端到底是：
   - `status=1`
   - `status=6`
   - 还是新的错误码
5. 不要再把 `wx.getSystemInfoSync is deprecated` 当成根因，那只是黄色兼容提示，不阻断支付。
