## Context

当前仓库已经完成了“把微信虚拟支付接进服务订单”的主干能力，但最近真实测试说明链路还没完全收口：

- 问题 A：开发版 Android 真机下单成功后，申请退款成功，但服务订单详情仍停留在普通处理中语义；样本订单 `332872263196571540` / `order_id=10417`
- 问题 B：体验版 Android 支付后用户侧感觉已成功，但本地订单仍是待支付并继续显示“去支付”；样本订单 `332874224676467417` / `order_id=10418`
- 旧遗留问题：外部支付相关入口仍可能带 `out_trade_no` 跳进订单详情，而当前部分接口仍只认内部 `order_id`

已经确认的事实：

1. 本地业务真源仍然应该是 `yoshop_order`，不是前端 success，也不是单独的 `payment_trade`
2. 当前 `10418` 存在两次虚拟支付尝试，两个 `out_trade_no` 的远端查询都只看到 `status=1`，本地订单一直没进入已支付
3. 当前 `10417` 的退款单 `10149` 已创建且审核状态为已同意，但本地退款单仍停留 `status=0`，说明“退款申请已发起”与“退款最终收敛完成”之间仍有缺口
4. 当前项目里仍残留少量“旧普通支付假设”，例如部分巡检/诊断逻辑没有完全按服务退款/虚拟支付语义识别

这说明现在不是某一个 if 写错，而是需要把支付、查单、通知、退款、补偿、状态投影、页面入口兼容一起拉通。

## Goals / Non-Goals

**Goals:**
- 明确并统一虚拟支付的认账真源与收口顺序
- 让支付成功、支付未最终确认、退款处理中、退款完成这几类状态在小程序端和后台端展示一致
- 让体验版/开发版、success 回调、主动查单、异步通知、补偿任务之间最终能收敛到同一个业务结果
- 修补支付相关入口的 `out_trade_no -> order_id` 兼容边界
- 建立一套可重复执行的“墨菲定律式”验收清单和证据留存方式

**Non-Goals:**
- 不重做整套订单系统
- 不把整个系统内部主键改成 `out_trade_no`
- 不新增独立虚拟商品库存/背包/发码体系
- 不为了修这个问题去改普通商品支付主流程

## Decisions

### 1. 继续坚持“内部业务主键 = order_id，外部支付标识 = out_trade_no”

**决策**
- 订单内部流转、页面跳转、后台管理、退款归属继续以 `order_id` 为主
- 只在支付相关外部入口、微信回跳/带参入口、查单兼容入口做 `out_trade_no -> order_id` 解析

**为什么这么定**
- `order_id` 是当前商城和服务订单体系的业务主键，改全站代价大、风险高
- `out_trade_no` 天然属于支付尝试维度；同一订单可能存在多次支付尝试，不适合作为整个业务订单的全局主键

**备选方案**
- 方案 A：全系统改为 `out_trade_no` 驱动 → 改动面太大，且多次支付尝试会把业务语义搞乱
- 方案 B：完全不兼容 `out_trade_no` 入口 → 会继续出现微信/支付相关入口跳不过来的问题

### 2. 把“支付认账”收口为统一状态机，不再让前端 success 单独决定结果

**决策**
- 前端 `requestVirtualPayment success` 只表示“用户侧支付动作返回成功”，不等于本地订单已认账
- 真正认账以“通知成功”或“主动查单确认已支付”触发 `orderPaySuccess` 为准
- 若即时查单仍是创建中/支付中，则保留待支付，但必须留下可继续补偿和重查的证据与路径

**为什么这么定**
- 体验版问题已经证明：success 可能先到，但后端即时查单未必已看到最终状态
- 如果前端一成功就直接写已支付，会引入假阳性；如果只查一次又立刻判失败，会引入假阴性

**落地规则**
- 成功回调后的第一次查单属于“快速探测”，不是最终裁决
- 对 `status=0/1` 这类未终态，进入“待收口”分支：记录最后一次支付尝试、提示用户稍后刷新、允许后台/补偿任务继续查
- 对 `status=2/3`，立即认账；`status=3` 继续补 `notify_provide_goods`
- 对重复支付尝试，始终只允许一个赢家交易推动订单进入已支付

### 3. 把“退款申请成功”和“退款完成”拆成两个明确阶段

**决策**
- 发起退款成功，只能代表平台受理了退款任务，不能直接把本地业务退款判成完成
- 本地退款完成必须由“退款通知”或“退款查询达到完成态”驱动 `finalizeVirtualRefund`
- 订单详情、退款页、后台详情都要优先显示“退款处理中/退款审核中/退款成功”等退款语义，而不是继续显示普通服务中/处理中

**为什么这么定**
- 订单 `10417` 已说明：退款申请发得出去，不代表本地状态已经完成收口
- 如果阶段定义不清楚，用户会看到“我都申请成功了，怎么页面还像没进入退款”这种错位

**落地规则**
- 退款中状态投影统一优先级：退款完成 > 退款处理中/审核中 > 普通服务状态
- 后台动作按钮遇到进行中退款时要统一收紧，避免“退款中还能开始服务/完成服务”等冲突动作
- 定时补偿必须扫描“已审核但未收敛”的虚拟支付退款单

### 4. 把“状态展示”和“按钮可操作性”抽成同一套投影规则

**决策**
- 用户端列表、用户端详情、退款页、后台详情、后台动作按钮都以同一套订单 + 退款投影规则出结果
- 不允许页面 A 说已支付、页面 B 还显示去支付；也不允许页面 A 显示退款中、页面 B 仍按普通处理中

**为什么这么定**
- 现在的问题本质上有一部分是“认账没收口”，另一部分是“展示没收口”
- 如果只修后端状态，不统一前端/后台按钮判断，仍会继续出现错位体验

**落地规则**
- 用户前台按钮：能否支付、能否退款、能否取消，必须先过退款态和支付态判断
- 后台按钮：开始服务、完成服务、服务前退款，要先过活动退款态判断
- 退款摘要、订单状态文案、服务状态文案使用统一优先级

### 5. 把验收方式从“手点一次看结果”升级为“带证据的链路验收”

**决策**
- 每一类关键场景都要留下证据：订单表、退款表、交易表、运行日志、前端运行环境、远端 query 结果
- 现有 `watch-live`、attempt trace、巡检命令继续复用，但要修正旧普通支付假设和服务退款识别错误

**为什么这么定**
- 虚拟支付很多问题不是稳定复现的，需要证据串起来才能定位
- 没证据就只能凭感觉判断“用户说成功了”，最后会很难收口

## Risks / Trade-offs

- [风险] success 之后如果把 `status=1` 立刻当失败，会制造“其实支付成功了但本地没认账”的假阴性  
  → Mitigation：把 `status=0/1` 当作“未终态”，进入后续补偿而不是直接当失败结案

- [风险] 如果所有入口都去兼容 `out_trade_no`，会把内部主键边界搞乱  
  → Mitigation：只在支付相关外部入口做映射，普通内部接口继续认 `order_id`

- [风险] 退款完成判断过早，会造成“钱没退干净，本地先显示已退款”  
  → Mitigation：只允许退款通知或查询完成态驱动 `finalizeVirtualRefund`

- [风险] 只修用户前台，不修后台动作与巡检脚本，后面还是会继续误操作或误判  
  → Mitigation：把后台按钮、诊断脚本、补偿任务一起纳入同一 change

- [风险] 体验版与开发版、Android 与其他环境在虚拟支付表现不完全一致  
  → Mitigation：验收矩阵里强制区分环境记录证据，不混着下结论

## Migration Plan

1. 先补规范和任务，明确“认账真源、退款阶段、状态优先级、入口兼容边界”
2. 先修不会扩大业务语义的收口点：状态投影、按钮判断、诊断脚本、支付相关入口兼容
3. 再修支付/退款收口逻辑中的查单、通知、补偿衔接问题
4. 用真实样本订单和新的验收矩阵复测开发版/体验版
5. 若发现某些场景仍受微信上游限制，则把“本地已收口”和“上游仍受限”明确拆开记录

## Open Questions

- 体验版样本 `10418` 的用户侧“支付成功”究竟是微信 success 先回、还是用户只完成了某一步但后端从未收到终态，这需要结合更完整的前端失败/回调证据继续核对
- 退款样本 `10417` 当前更偏向“本地退款收口未完成”还是“远端退款仍未进入完成态”，需要补一次最新查询证据后再下最终结论
- 哪些外部支付入口需要兼容 `out_trade_no`，除了订单详情外是否还包括订单查询、订单管理跳转或客服回链，需在实施时按真实入口逐项确认
