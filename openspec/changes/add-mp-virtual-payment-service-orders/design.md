# Design: WeChat Virtual Payment 2.0 for Service Orders

## Overview

本方案采用“新增支付通道 + 复用服务订单”的设计。

核心原则：

1. 业务订单仍然是商城订单
2. 订单语义仍然是现有服务订单
3. 微信虚拟支付只负责扣款、查单、退款、异步通知
4. 商家确认、服务中、完成服务、退款审核继续复用现有体系
5. 首期只做最小闭环，不为未来复杂营销和多规格预埋过度设计

## First-Principles Decisions

### 为什么不新建“虚拟商品订单体系”

因为当前项目已经拥有完整的服务订单引擎：

- 服务订单识别逻辑已存在
- 服务订单状态文案已存在
- 商家开始服务 / 完成服务动作已存在
- 服务退款模式已存在

如果再新建一条“虚拟支付订单体系”，会平白引入第二套订单状态、第二套后台操作、第二套退款判断，复杂度远大于收益。

因此：

- 支付层新增
- 订单层复用

### 为什么 `productId` 只做支付映射

从第一性原理看：

- 用户买的是“游戏服务”
- 微信要求付的是“支付侧道具”

这两个对象不是同一个概念。

因此最合理的建模是：

- 商城商品负责业务履约
- `productId` 只负责满足微信支付接口要求
- 两者通过后台配置进行一对一映射

### 为什么首期启用固定总价模式

当前项目的服务订单结算后端仍然会执行：

- 会员等级折扣
- 优惠券
- 积分抵扣

而微信虚拟支付要求支付价格与道具价格保持稳定对应。

一旦允许商城营销改价，就会出现：

- 商城应付价变化
- 微信 `productId` 价格固定
- 退款金额、查单金额、订单金额难以一致

因此首期不去改造一套泛化的“固定总价模式”，而是采用更窄的约束：

- 仅支持单商品立即购买
- 结算时若存在任何改价输入或最终应付金额不等于价格快照，则直接拒绝支付
- 首版不为虚拟支付商品适配复杂营销改价链路

## Business Model

### Domain Objects

- 服务商品：商城中的业务商品
- 服务订单：商城订单主体
- 虚拟支付映射：服务商品到微信 `productId` 的配置
- 虚拟支付交易：记录微信虚拟支付过程的交易单据

### Recommended Mapping Model

首期采用“商品级固定映射”：

- 一个服务商品绑定一个 `productId`
- 一个服务商品绑定一个固定价格
- 一个服务商品一次只能购买一个服务数量

建议字段：

- `vp_enabled`
- `vp_product_id`
- `vp_price_snapshot`

首期不建议引入：

- SKU 级多映射
- 动态匹配 `productId`
- `activitySellingPrice`
- `buyQuantity > 1`
- `zoneId`

### Mapping Rules

映射规则固定如下：

- 商品必须是现有服务商品
- 商品必须配置 `vp_enabled=1`
- 商品必须绑定一个有效 `productId`
- 商品必须记录一个平台价格快照
- 下单与支付前必须校验商城售价与平台价格快照一致

## Architecture

### Existing Flow to Reuse

复用现有：

- 商品详情页服务商品识别
- 服务订单立即购买
- 服务结算页
- 订单创建
- 后台开始服务
- 后台完成服务
- 服务退款申请与审核

### New Components

新增以下能力：

1. 虚拟支付内部支付路由与收银台分支
2. 商品虚拟支付映射配置
3. 虚拟支付交易表
4. 虚拟支付参数生成接口
5. `wx.requestVirtualPayment` 前端适配器
6. 虚拟支付查单 / 通知 / 退款服务
7. 后台虚拟支付配置项

## Data Design

### 1. 商品映射字段

按剃刀定律，首期优先直接挂在商品表，不单独设计复杂关联表。

建议在商品表新增字段：

- `vp_enabled` tinyint
- `vp_product_id` varchar
- `vp_price_snapshot` int

说明：

- `vp_enabled=1` 表示该商品走虚拟支付
- `vp_product_id` 存微信道具 ID
- `vp_price_snapshot` 使用“分”存储，表示后台录入的微信平台价格快照

首期权威关系固定如下：

- 商品当前售价是商城业务真源
- `vp_price_snapshot` 是支付侧审核与对账参考
- 保存商品时要求两者一致
- 发起支付时再次校验两者一致
- 若不一致则硬失败，不做自动同步、不做静默修正

因为你当前是按不同价格创建不同商品，这个模型最顺手，后续新增价格商品时只需新增商品并配置对应 `productId`。

### 2. 支付事实持久化

首版只需要满足三件事：

- 按 `out_trade_no` 做幂等
- 保留支付/退款的最小平台事实用于对账
- 保留通知原文或关键快照用于排障

实现上优先评估是否能复用现有 `yoshop_payment_trade`；若现有模型无法承载虚拟支付最小事实，再新增独立的 `yoshop_virtual_payment_trade`。

无论采用哪种落点，首版最小字段集合都应覆盖：

- `order_id`
- `order_no`
- `user_id`
- `env`
- `product_id`
- `goods_price`
- `out_trade_no`
- `platform_order_id`
- `platform_refund_id`
- `notify_times`
- `last_notify_time`
- `payload_snapshot`
- `create_time`
- `update_time`

它只负责记录外部支付事实、平台返回值和对账信息，不承担业务状态流转。

业务状态真源固定如下：

- 订单表：支付后的业务订单状态
- 退款表：退款申请与审核业务状态
- 虚拟支付交易表：外部平台流水与通知快照

### 3. 服务端配置项

虚拟支付配置不应继续保存在仓库文档中。

首版只要求服务端存在可靠配置来源，例如部署密钥、环境变量或现有服务端配置体系：

- `enabled`
- `env`
- `offer_id`
- `sandbox_app_key`
- `production_app_key`
- `merchant_id`
- 回调基础域名

`wxapp_setting` 继续负责小程序 `app_id / app_secret`。

后台配置页不是首版闭环前置条件；若后续有明确运营维护需求，再补管理入口。

## Payment Flow Design

### User Flow

```text
商品详情页
  -> 立即下单
  -> 服务结算页
  -> 创建待支付服务订单
  -> 收银台显示“微信支付”
  -> 若订单商品启用虚拟支付，则走虚拟微信支付分支
  -> 后端生成 signData / paySig / signature
  -> 前端调用 wx.requestVirtualPayment
  -> 支付成功后回到订单页
  -> 后端通过通知或查单收敛最终支付状态
  -> 订单进入 待联系
```

### Cashier Strategy

用户要求收银台仍显示“微信支付”和微信图标。

实现策略：

- UI 层继续展示“微信支付”
- 收银台对外仍只显示并提交 `wechat`
- 服务端支付分发器根据订单是否命中虚拟支付能力来决定实际调用：
  - 普通商品 -> 普通微信支付实现
  - 虚拟支付服务商品 -> 虚拟支付实现

这样既满足用户体验一致，也避免把局部能力扩散成全局支付枚举改造。

### Order Creation Timing

建议先创建商城待支付订单，再发起虚拟支付。

原因：

- 订单号、用户、商品、金额在支付前就有稳定归属
- 支付成功后容易直接把结果回写到已有订单
- 退款、查单、售后能全部围绕既有订单工作

因此：

- `outTradeNo` 单独生成
- 但必须关联到已创建的商城订单

### Virtual Payment Parameter Strategy

首期固定使用：

- `mode=short_series_goods`
- `buyQuantity=1`
- `currencyType=CNY`
- 不传 `zoneId`
- 不为虚拟支付商品适配复杂改价链路

后端返回给前端的最小参数集：

- `mode`
- `paySig`
- `signature`
- `signData`

其中 `signData` 内至少包含：

- `offerId`
- `env`
- `currencyType`
- `buyQuantity`
- `productId`
- `goodsPrice`
- `outTradeNo`
- `attach`

### Signature Strategy

服务端统一负责：

1. 读取当前环境配置
2. 选择沙箱或现网 `AppKey`
3. 组装规范的 `signData`
4. 计算 `paySig`
5. 生成用户态 `signature`

前端禁止参与签名拼装。

## Order State Reuse

### State Ownership

状态归属必须明确，否则实现时会在查单、通知、退款之间互相打架。

本方案固定：

- “是否已支付成功”以订单表最终 `pay_status` 为业务真源
- “是否已进入退款流程 / 退款完成”以现有退款表为业务真源
- 虚拟支付交易表只记录平台侧事实，不单独拥有业务履约状态

直接复用现有服务订单流转：

- 未支付：`待支付`
- 支付成功且未开始服务：`待联系`
- 商家确认：`服务中`
- 商家完成：`已完成`
- 退款成功：沿用当前退款完成态

重要约束：

- “商家确认”直接等于“开始服务”
- 不增加“已确认未开始”的新状态

## Refund Design

### Refund Decision Layer

继续复用现有订单退款规则判断：

- `未开始服务` -> 自动退款
- `服务中` -> 用户申请，商家审核
- `已完成` -> 不可退款

### Refund Execution Layer

资金退回改走微信虚拟支付退款接口。

也就是说：

- 退款“该不该退”仍由现有服务订单规则判断
- 退款“钱怎么退”改由虚拟支付退款服务执行

实现上建议把“退款判定”和“退款执行”拆开，但这属于实现手段，不是首期闭环前置条件。

### Refund Consistency

退款执行必须做到：

- 本地退款单与微信退款任务一一关联
- 重复提交不重复发起平台退款
- 审核通过后才真正调起平台退款
- 自动退款和人工审核退款共用同一套平台退款执行器

## Notification and Reliability

### Reliability Principle

不能依赖小程序前端 `success` 回调作为最终支付成功依据。

必须同时具备：

- 前端支付后的状态刷新
- 服务端查单兜底
- 异步通知幂等处理

### Notification Strategy

首期建议实现：

1. 支付成功后的服务端状态确认
2. 重复通知幂等处理
3. 支付状态查单接口
4. 退款结果通知处理

### 支付后平台动作

若微信虚拟支付链路存在支付成功后的平台侧确认动作，其触发时机必须先以官方接口契约为准再实现。

在该契约未确认前：

- 不把这一步写死进首版必做闭环
- 不把人工服务完成态与平台侧确认动作绑定
- 只先保证商城订单能依靠通知或查单正确收敛到已支付

## Backoffice Design

### 商品配置

后台商品编辑页新增：

- 是否启用虚拟支付
- 绑定 `productId`
- 绑定平台价格快照

保存时校验：

- 必须是服务商品
- 商品售价必须与平台价格快照一致
- 非服务商品不能开启虚拟支付

### 虚拟支付配置

首版要求服务端可读取以下配置，但不要求必须提供后台维护入口：

- 开关
- 当前环境
- OfferID
- 沙箱 AppKey
- 现网 AppKey
- 商户号
- 回调基础域名

### 订单详情

后台订单详情增加只读信息：

- 是否虚拟支付
- 虚拟支付交易号
- `productId`
- 支付环境
- 支付状态
- 退款状态
- 最近通知时间

## Integration Readiness

你目前已经提供了：

- AppID
- OfferID
- 沙箱 AppKey
- 现网 AppKey
- 微信支付商户号
- request 合法域名
- 多个 `productId`

以下资料不是“可选补充”，而是通知 / 查单 / 退款功能进入开发前的开工 gate。

### 开工前必需资料

- 小程序虚拟支付能力开通截图或说明
- 沙箱联调说明
- 现网开通说明
- 虚拟支付退款接口接入说明
- 虚拟支付异步通知样例
- 虚拟支付查单接口样例
- 当前小程序 `openid` / 登录换取链路说明

若以上资料未确认，则首版只能先实现商品映射、下单参数生成和前端拉起支付，通知 / 查单 / 退款任务应冻结，不进入闭环验收。

### 建议补充资料

- 支付成功通知样例报文
- 退款成功通知样例报文
- 错误码清单
- 官方签名算法示例
- 上架审核要求或类目限制说明

### 不需要首期提供的资料

- `zoneId`
- 区服维度配置
- 角色维度参数

因为首期明确不做这条分支。

## Recommended First Release Scope

首期只做最小可用闭环：

- 仅微信小程序
- 仅服务商品
- 仅立即购买
- 仅单商品、单数量
- 仅商品级固定 `productId` 绑定
- 仅虚拟微信支付
- 仅在金额完全一致时允许支付
- 先跑沙箱，再切现网

这条路径最符合你当前商品建模方式，也最容易在现有 YoShop 代码上稳定落地。
