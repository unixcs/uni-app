# Proposal: Add WeChat Mini Program Virtual Payment for Service Orders

## Intent

为当前 YoShop 二开微信小程序接入微信虚拟支付 2.0，用于销售“游戏服务”类商品，并复用现有商城中的服务订单状态机、商家确认流程、完成流程和退款流程。

本变更的目标不是新增一套独立的“虚拟商品系统”，而是把“微信虚拟支付”作为新的小程序支付通道，把“游戏服务”继续落在现有服务订单体系中。

## Why

当前项目已经具备以下关键能力：

- 小程序商品详情、立即下单、结算、收银台链路已存在
- 服务订单状态流已存在：`待支付 -> 待联系 -> 服务中 -> 已完成`
- 服务订单退款模式已存在：
  - 服务开始前：自动退款
  - 服务开始后且未完成：用户申请，商家审核
  - 服务完成后：不可退款

因此最稳妥的方案是：

1. 保留“服务订单”作为业务订单语义
2. 把微信虚拟支付 2.0 作为微信小程序端新的支付实现
3. 把虚拟支付中的 `productId` 视为“支付侧映射道具”，不是商城业务商品本体
4. 对虚拟支付服务商品执行金额一致性约束，保证商城应付金额与微信道具价格一致

## Scope

本期范围：

- 支持微信小程序内购买“游戏服务”商品
- 支持通过 `wx.requestVirtualPayment` 发起虚拟支付
- 服务端完成签名、下单参数生成、支付结果校验、查单兜底
- 支付成功后复用当前服务订单状态流
- 复用当前服务订单退款规则
- 后台可继续执行开始服务、完成服务、审核退款
- 后台支持给服务商品配置虚拟支付映射
- 虚拟支付密钥与环境配置脱离仓库明文文档，首版优先走服务端部署配置

## Non-Goals

本期不做：

- 不新增独立的虚拟币体系
- 不做游戏内背包、库存、发码、道具库存体系
- 不做区服 / `zoneId` / 角色维度扩展
- 不做多商品混合结算
- 不做购物车结算
- 不做部分退款、拆单退款
- 不做 H5、APP、公众号端虚拟支付

## Product Decisions

### 1. 业务模型

用户购买的是“游戏服务”，不是“虚拟币充值”。

- 商城里的主业务实体仍然是服务商品 / 服务订单
- 微信虚拟支付只负责完成微信侧扣款
- 支付成功后订单进入现有服务订单状态流

### 2. 商品与 `productId` 绑定策略

首期采用最简单、最稳定的绑定规则：

- 按商品维度绑定一个固定 `productId`
- 一个服务商品对应一个固定价格
- 一个服务商品对应一个微信虚拟支付道具
- 首期 `buyQuantity` 固定为 `1`

这样可以直接支持你后续在商城后台新增不同价格的新商品：

- `0.01` 商品绑定 `vip0`
- `9.9` 商品绑定 `vip9`
- `88` 商品绑定 `vip88`
- 后续新增 `158/168/199/...` 时，新增商品并绑定对应 `productId` 即可

不建议首期按 SKU 做复杂映射，也不建议一个商品动态匹配多个 `productId`，因为那会显著增加价格校验、后台配置和退款对账复杂度。

### 3. 支付入口策略

虚拟支付作为收银台里的“微信支付”展示给用户：

- 继续显示“微信支付”名称
- 继续使用现有微信图标 UI
- 对外仍保留单一 `wechat` 支付选项
- 仅在服务端支付分发时，根据订单是否命中虚拟支付能力，路由到虚拟支付实现

也就是说：

- 对用户来说，还是“微信支付”
- 对系统来说，普通微信支付和虚拟微信支付是同一支付入口下的两条内部实现链路

### 4. 订单状态策略

复用现有服务订单状态，不新增中间状态：

- 待支付
- 待联系
- 服务中
- 已完成

并接受以下映射：

- 虚拟支付成功但商家未确认：`待联系`
- 商家确认：等于开始服务，订单进入 `服务中`
- 商家完成：进入 `已完成`

### 5. 退款策略

完全复用现有服务订单退款判定：

- 支付后、商家未确认前：自动退款
- 商家确认后、服务未完成前：用户申请退款，商家审核
- 商家完成服务后：不可退款

差异只在于：

- 退款的资金退回动作不再走普通微信支付退款
- 而是走微信虚拟支付退款接口

实现上必须先把“退款判定”和“退款执行”拆开：

- 退款判定继续复用现有服务订单规则
- 退款执行改由虚拟支付退款执行器负责

### 6. 优惠策略

按剃刀定律，首期不引入泛化的“固定总价模式”，只增加一条更窄的结算约束：

- 虚拟支付商品仅支持单商品立即购买
- 只要存在任何改价输入，或最终应付金额不等于价格快照，就直接拒绝支付

原因：

- 微信虚拟支付本质上要求支付价格绑定到具体 `productId`
- 当前服务订单后端仍会跑多种改价逻辑
- 如果保留这些能力，会导致商城订单应付金额和微信虚拟道具价格不一致

因此首期最稳妥的策略是：

- 每个虚拟支付服务商品有一个固定售价
- 该售价必须与所绑定 `productId` 的平台价格快照一致
- 结算时若金额不一致则硬失败，不做自动修正

## Success Criteria

- 用户可以在微信小程序购买游戏服务并完成虚拟支付
- 支付成功后订单进入现有服务订单流
- 商家可以继续使用“开始服务 / 完成服务 / 审核退款”
- 自动退款和审核退款行为符合现有服务订单规则
- 支付回调或重复推送不会重复履约、重复退款
- 服务端可读取非源码明文的虚拟支付密钥、环境、商品映射
- 沙箱环境先完整闭环，再切现网参数
